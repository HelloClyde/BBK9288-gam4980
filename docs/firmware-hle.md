# 固件与游戏 HLE

## 范围

“HLE”是游戏选择界面中的加速开关，默认开启。9288 构建启用项目所带
`E.BIN` 中多段已确认的热点：`$650F-$66FC` 的普通字形合成、
`$608A-$61C4` 的 32 像素宽字形合成、`$7933-$7940` 的直接存储器字节填充、
`$6A75-$6B04` 的位图移位写入、`$6B1A/$6BA4-$6C80` 的公共图片行尾、
`$5CB3-$5D04` 的位图移位复制，以及
`$D1A2-$D200` 的 16×16 位无符号乘法（保留低 16 位结果）和 `$D340-$D361`
的 16 位比较。另有一组面向旧 A 系列 C 编译器 ABI 的跨游戏运行库 HLE：
`$F52A-$F5BC` 的四窗口 bank 切换、`$D2CA-$D2F5` 的 `__and_long`、
`$D596-$D5A5` 的 `__ld_oper1_temp_store_addr`、`$D362-$D39A` 的
`__cmp_long`，以及 `$D572-$D585` 的 `__indirect_call`。图形快速路径
一次处理一行、一次完整填充或一个位图单元；其中 `$5CB3` 和 `$6A75` 会在同一
CPU 时间片内批量完成尽可能多的完整位图单元。乘法快速路径一次完成整个子程序。
它不是整个固件的 HLE。加载 `.gam` 时还会按函数骨架识别游戏自己的计数循环、
2 位位图循环、对象数组扫描递减循环、正向和反向三字节记录处理、二级对象表查询
链，以及跨 `$D6AF->$D1A2` 乘法调用的完整对象处理流程；位图路径会继续融合上层
取源字节、子像素合成、宽度判断、换行和下一行地址计算，并能从子像素尾部或
源字节尾部恢复融合。匹配只建立固定描述表，不修改游戏代码，也不
生成机器码。

## 安全条件

- 每次进入先检查虚拟 PC 对应的 E.BIN 物理 bank。
- `$6A75` 路径首次命中会逐字节校验完整 144 字节函数签名和相关只读固件
  常量；`$5CB3` 路径会对完整 82 字节循环做双重 32 位散列校验；`$650F`
  路径会对 `$650B-$66FC` 的完整例程做双重 32 位散列校验；`$608A` 路径
  另外校验 `$6086-$61C4` 的 319 字节双重散列；`$7937` 路径校验
  `$7933-$7940` 的完整 14 字节循环；`$D1A2` 路径对 `$D1A2-$D200` 的
  完整 95 字节子程序做双重 32 位散列校验。
- 乘法和移位/字形路径只处理非十进制模式，移位量还必须在 0..7；其他情况
  回退现有 AOT 或解释器。
- 快速路径计算并保留原始 6502 周期数。`$5CB3` 和 `$6A75` 每完成一个客机
  循环就重新检查剩余周期预算、HLE 状态、bank、十进制标志和终止条件，只在
  当前 CPU 时间片还能容纳下一次完整循环时继续；其余路径若容纳不下完整循环，
  本次不使用 HLE。所有路径都不会跨过调度或中断检查边界。
- 游戏函数匹配不依赖整个 GAM 签名或固定函数地址；它校验 opcode、分支/跳转
  目标关系、零页操作数关系和固件调用 ABI，再从当前函数提取地址与常量。
- 固件 C 运行库按单个函数的物理入口和完整函数双散列校验，不因 GAM 文件名、
  文件总哈希或游戏代码重定位而失效。
- 不申请堆内存、不生成可执行 RAM；游戏函数匹配结果使用有上限的固定描述表。

## 旧 A 系列编译器符号与跨游戏画像

`BBK旧A系列C语言开发包/dwn/test.map` 给出了 E.BIN 运行库的原始符号范围。map
中的 `runtime_program` 地址比当前客机虚拟地址低 `$4000`，例如 map 的 `$92CA`
对应运行时 `$D2CA`。不能只凭函数名照搬旧固件清单：开发包中的 3288 汇编清单
把通用程序基址放在 `$03BC/$03BB`，而项目实际 E.BIN 的 `$F52A` 机器码读取的是
`$03D6/$03D5`。实现必须以随程序发布的 E.BIN 机器码为最终依据，旧 map/list 用于
恢复符号名、ABI 和算法意图。

对《伏魔记》《三国霸业6980-方案一》《魔塔之怀旧终曲》各运行 600 客机帧的
非 HLE 画像显示，三者共同使用 `__cmp_int`、`__cmp_long`、
`__banked_function_call`、`__ld_oper1_temp_store_addr`、`__indirect_call` 和函数参数
压栈助手。现有 `__cmp_int` HLE 已覆盖第一项；本轮新增 bank 切换、长整数与、
操作数地址装载、32 位比较和间接调用。`__banked_function_call` 会跨入任意游戏
目标函数，不能像普通叶函数一样一次原子替换；当前先 HLE 它依赖的通用
`__indirect_call`，后续若继续优化，应把调用前缀和返回后缀做成两个可恢复阶段。

随机精确状态回归分别覆盖 30,000 组 bank 切换入口/内部入口，以及每个 C 运行库
叶函数 10,000 组输入，逐项比较 CPU、标志、返回栈、完整 32 KiB RAM、bank 映射
和客机周期。在三份 GAM 的 600 帧集成回归中，HLE 开关两组的最终画面 FNV 与
完整状态哈希均逐项相同。新增路径在该窗口内的实际命中如下：

| 游戏 | bank 切换 | `__and_long` | 地址装载 | `__cmp_long` | 间接调用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 伏魔记 | 3,125 | 0 | 104 | 197 | 1,620 |
| 三国霸业 | 7,817 | 5,894 | 587 | 6,061 | 4,166 |
| 魔塔之怀旧终曲 | 5,528 | 9,337 | 959 | 9,944 | 2,800 |

这些是通用覆盖量和等价性证据，不是真机帧率。

客机总周期以及包含 CPU、RAM、Flash、bank、Timer 和 LCD 的状态哈希完全一致。
60、120、600、3300、3600、4200、5000 和 8000 帧的中间检查点也全部一致。

HLE 入口复用现有 AOT 分派器的 `$5CB3`、`$608A`、`$650F`、`$6A75` 和
`$7937`、`$D1A2` case，不在解释器公共退出路径增加判断。收益受限于这些
固件循环原先已被静态 AOT 基本块覆盖；
HLE 是在已经原生化的 C 超块之上合并分支和状态更新，并非从纯逐指令解释直接
跃升。

游戏位图跨行融合使用 `$50EB-$5195` 的局部函数骨架匹配，不依赖《伏魔记》
整文件签名或固定物理地址。它仍以完整源字节、子像素尾部、源字节尾部或完整换行
为最小提交单元；若当前 0x800 周期切片放不下下一单元，就保存原 PC/寄存器状态并
交回调度器。10,000 组随机换行状态在 O0、O2 下逐项比较 CPU、完整 32 KiB RAM
和客机周期均一致，原有 40,960 组位图差分也全部通过。8000 帧剧情回归的画面
FNV、总周期和完整状态哈希仍分别为 `aafca923`、`419678986` 和
`21f0b8f76cc52f8d`。相对加入反向记录 HLE 后的画像，剩余逐指令执行从
1,919,880 降至 1,716,401，减少 203,479 条（10.60%）；目标物理函数自身从
263,146 降至 59,667 条，减少 77.33%。

正向三字节记录扫描还把 `$7B9E-$7CAC` 拆成首字节、第三字节、第二字节和索引
加三四个可恢复阶段。`$7BFE-$7C42` 按加载时 AOT 的真实超块边界整体替换：即使
剩余预算比该块短，也与原 AOT 一样执行到分支边界并返回准确的超额周期，而不是
错误地提前停在块中间。完整记录的 10,000 组差分以及四个恢复入口的 27,500 组
O0/O2 差分全部一致；8000 帧状态哈希仍为 `21f0b8f76cc52f8d`。该路径预算回退
从 1,317 次降到 104 次；相对跨行位图版，剩余指令从 1,716,401 降至
1,603,205，减少 113,196 条（6.59%），目标正向扫描区域减少 86.52%。

新增 `$D1A2` 乘法 HLE 用边界值和随机输入做了 20000 组逐状态差分，逐项比较
CPU 寄存器、标志、返回地址、客机周期和完整 32 KiB RAM。旧五条 HLE 与新增
乘法 HLE 的 8000 帧最终状态哈希同为 `cce27fe3837c2f7b`；乘法路径额外命中
13687 次，替代 3454468 个客机周期，并少执行 877495 条逐指令/AOT 画像指令。
这些数字描述命中范围，不代表 S1C33 真机加速比例。

三字节记录查找路径对 10,000 组随机 RAM、CPU、PC、标志和周期预算做了逐状态
差分，并覆盖第一、第二、第三字节不匹配、完整匹配及跨记录批处理。8000 帧最终
状态哈希仍为 `21f0b8f76cc52f8d`，游戏 AOT/逐指令画像由 348,041 条降到
218,801 条，剩余解释器画像由 2,954,276 条降到 2,372,664 条，分别下降
37.1% 和 19.7%。

二级对象表查询链从保存的对象基址恢复上下文，完成 16 位偏移相加、选择器索引、
二级表取值、对象字段写回，并准备下一次乘 5 调用。它只合并一个原本为 79 条
6502 指令的完整过渡块，不越过下一次固件调用或时间片边界。8 个重定位实例共做
了 12,000 组随机 CPU、栈、RAM、映射和周期预算差分。8000 帧最终画面校验为
`aafca923`、客机周期为 `419678986`、完整状态哈希仍为
`21f0b8f76cc52f8d`；剩余逐指令画像由 2,372,664 条进一步降到 2,141,036 条，
下降 9.76%，相对最初约 400.1 万条已累计下降约 46.5%。这些仍是覆盖率，不能
直接换算为真机帧率。

完整对象处理流程把原先被 `$D6AF->$D1A2` 乘法切开的两个大基本块合并为一个
原子路径，计算两组对象边界、索引乘 5、二级表查找和对象字段写回，最后按原程序
的第一个时间片边界进入 `$DAAA`。两份重定位实例做了 10,000 组随机 CPU、栈、
RAM、跨页地址和周期预算差分；8000 帧中尝试 1,022 次、完整命中 826 次，另有
196 次因周期不足回退，替代 593,546 个客机周期。最终画面、总周期和完整状态
哈希不变，剩余逐指令画像由 2,141,036 条降到 2,027,048 条，下降 5.32%。

反向记录处理从 `$7D34` 接管三段字节比较、失败后的首字节复核、索引减 3 回边，
并融合命中标志或 `$1937` 错误状态收尾。函数局部 386 字节骨架匹配成功后才建立
描述项；10,000 组 O0/O2 随机 CPU、跨页 RAM、匹配分支、批处理和周期预算差分
全部一致。8000 帧中尝试 494 次，306 个批次执行 689 个记录，单批最多 4 个，
覆盖 335,999 个客机周期；最终画面、总周期和完整状态哈希不变。剩余逐指令画像
由 2,027,048 条降到 1,919,880 条，再下降 5.29%。

二级对象表查询链在同场景真机轻量日志中把 15.213 fps 提高到 15.406 fps，约
提升 1.27%，明显低于它的画像降幅；因此后续不再堆同等级短块，而优先选择能跨
多个基本块和固件调用的完整流程。完整对象处理流程的同场景真机日志从
15.406 fps 提升到 17.223 fps，约快 11.8%，验证了扩大融合范围的方向。

在 9288 指令级模拟器上，新增路径后的游戏菜单截图与已知正确版本逐字节一致，
159×96 客机画面仍严格按 2× 输出，系统菜单退出后的桌面截图也与已知正确版本
逐字节一致。这是等价回归；模拟器的主机运行耗时不作为性能结论。

为降低高命中率短循环的宿主开销，`$5CB3` 和 `$6A75` 后续增加了时间片内批量
执行。8000 帧轨迹中，两条路径每次进入 HLE 分别平均完成约 8.69 和 8.52 个
客机循环，最大批量分别为 18 和 16；开启和关闭 HLE 在 8 个中间检查点以及最终
CPU、RAM、Flash、bank、Timer、LCD 状态哈希均完全一致，命中次数与替代的客机
周期也没有变化。PC 端 `-O0` 配对测试中位耗时由 1654.89 ms 降至 1316.14 ms，
约快 25.7%；这个数字只证明减少分派的方向有效，S1C33 真机收益必须由同场景
`PERF.LOG` 判断。

在批量执行之上，`$5CB3` 和 `$6A75` 还提供经验证 RAM 的直接指针路径。进入
循环前按 256 字节映射页检查源区间连续可读、目标区间连续映射到客机 RAM，且
整段地址不越过 64 KiB 虚拟空间；`$5CB3` 会额外排除端口和具有写副作用的地址，
`$6A75` 则只接受已确认的 LCD RAM 范围，并保留 `$0400` 写到物理 `$1000` 的
固件特例。全部条件满足时，整个批次直接读写缓存后的宿主指针，不再让每个字节
经过 `mem_read` / `mem_write` 的页表与端口分派；任何条件不满足都会回退原有
通用批处理路径。

使用《伏魔记》做 8000 帧剧情输入时，`$5CB3` 的 426,670 次批处理迭代和
`$6A75` 的 786,025 次批处理迭代均进入直接路径；HLE 开/关的画面、客机周期和
完整状态哈希仍分别为 `aafca923`、`419678986` 和
`21f0b8f76cc52f8d`。S1C33 同源对照构建中，启用直接路径的 `s6502_exec` 反而比
禁用时小 160 字节，两个独立助手合计 1,994 字节，净代码增量约 1.8 KiB。
PC 端 `-O0` 八组交替配对计时中位数由 1242.73 ms 降至 1185.02 ms，约快
4.64%。这些数据验证覆盖率、等价性和优化方向；实际速度提升仍以真机同场景
日志为准。

真机同场景结果否定了把这条实验路径作为默认实现：客机周期/帧基本不变，
但 cycles/s 从 621,767 降到 594,835，fps 从 9.354 降到 8.948，约慢
4.33%。这说明 S1C33 上额外的区间检查、指针准备和较大的代码路径抵消了直接
访问收益。正式构建现已默认停用直接 RAM 路径，保留原有批量 HLE；只有显式定义
`GAM4980_ENABLE_DIRECT_RAM_HLE` 才会重新启用该实验，不能根据 PC 端结果发布。

### `$5C5D` 完整绘图行实验

`build_9288.py --aggressive-region-hle` 会在位图例程完成参数准备后，从 `$5C5D`
接管完整绘图行，包括首字节遮罩、`$5CB3` 内层复制、右边缘遮罩、源/目标步进和
行计数。首次命中会对 `$5C5D-$5E01` 的完整 421 字节做双重 32 位散列校验；
源区或目标区可能触及端口/控制字段时直接回退原路径。

最初“一次完成整个矩形”的实现虽然单次函数开销更低，却会跨过 0x800 周期 CPU
切片，60 帧状态回归立即发现 Timer/IRQ 顺序变化，因此没有保留。当前实现先估算
下一完整行的精确客机周期，只在当前切片容得下时执行，可在一次调用中合并多行；
放不下时不修改任何状态并回退 AOT/解释器。

随机宽度、行数、移位和遮罩的 3000 组差分逐项比较了 CPU、返回栈、完整
32 KiB RAM、LCD 脏标志和客机周期，全部一致。《伏魔记》在 60、120、600、
3300、3600、4200、5000 和 8000 帧的完整状态哈希也与默认路径逐点一致，最终
均为 `21f0b8f76cc52f8d`。8000 帧中该实验合并 1,629 次调用、处理 3,673 个
完整绘图行、覆盖 2,152,422 个客机周期；扣除原 `$5CB3` 批处理已经覆盖的部分，
HLE 净新增覆盖 1,430,476 个周期。模拟器已验证加载和游戏画面无字形/位图回归，
实际加速比例仍只能由同场景真机轻量日志判断。

### `SysPicture` 公共图片行尾

旧 A 系列开发包的 `dwn/test.map` 把 E.BIN `$6792` 标为 `SysPicture`。三款游戏
的非 HLE 画像表明，图片模式 3/4 都会反复经过 `$6B1A` 或 `$6BA4`，随后在
`$6C18-$6C80` 完成最后一个遮罩字节、源指针推进、`$6646` LCD 行地址换算、
行号和剩余行数更新。该链属于固件公共图形 API，不依赖 GAM 文件签名或函数
地址，因此比继续添加单游戏短块更适合作为跨游戏 HLE。

快速路径只接受开发包和当前 E.BIN 已验证的模式 3/4、0..7 位移量、标准
`$0400->$1000` LCD 别名以及安全目标地址；其他图片模式、非常规 page-3 映射、
特殊目标区或不足的当前周期预算全部回退原 AOT 路径。实现同时还原 AOT 链内部
的 `ea/et/dt` 暂存状态，避免在同一个 `s6502_exec` 时间片继续执行时发生周期或
分派漂移。

模式 3/4、两个行尾入口、边界行地址、1/2 行结束和 `$0400` 别名共做 3,000 组
随机差分，逐项比较周期、CPU、完整 32 KiB RAM 和 LCD dirty 状态；原有整行
HLE 的 3,000 组回归也同时通过。HLE 开/关对比中，《伏魔记》5,000 帧（含开场
输入脚本）以及《三国霸业》《魔塔之怀旧终曲》各 2,000 帧的画面 FNV 和完整
状态哈希完全一致。新路径分别命中 34,259、4,423 和 1,631 次。这些数据证明
公共覆盖与等价性，真机速度仍以轻量日志为准。

对用户提供的《伏魔记》卷首文字页取连续 100 个客机帧，未合并轨迹共有
1,616,841 条 6502 指令。新增的宽字形与直接存储器填充 HLE 共命中 4,176 次，
替代 1,048,547 个客机周期，约占该窗口 6,666,667 个 CPU 周期的 15.73%；
连同原有三条 HLE，总计替代 2,596,309 个周期，覆盖约 38.94%。同机 4400 帧
主机端测试的中位耗时由约 140.9 ms 降至 137.0 ms；该数字包含启动和 ROM
载入，只用于确认方向，不等同于真机帧率。

`$7937` 循环中的 `LDA $03` 不能按普通零页读取实现。`$03` 是第四个直接
存储器数据端口，每次读取都可能自动推进物理地址；首版若直接访问 `ram[3]`，
卷首文字会被读成 0。现实现每次迭代都走 `READ8(0x0003)`，保留端口副作用，
并重新读取间接目标指针以保留低 RAM 别名语义。

`$650F-$66FC` 最初虽然通过了 x86 状态回归，S1C33 的 `-O2` 构建却会把菜单
金额 `500` 绘制成错误符号。原因是目标后端会误编译这段包含大量窄值和间接
内存调用的辅助函数。现实现把完整字形行拆成独立的全宽计算，并只对该函数使用
Clang `optnone`；32 像素宽字形使用同样的目标端保护，主解释器、AOT 和其他
HLE 仍为 `-O2`。使用同一份
《伏魔记》、同一输入对比时，字形 HLE 开/关的金额菜单、系统子菜单和返回标题
截图逐字节一致，系统退出后均返回桌面并稳定 20 秒。

### 公共图形 API 链

旧 A 系列开发包的 `dwn/test.map` 和 `DICTSYS.H` 已用于恢复公共图形 API 的
边界与参数语义。当前实现不依赖单个 GAM 的完整签名，而是在 E.BIN 固件签名
通过后覆盖下列公共热链：

- `SysPicture`：参数准备、完整位图行、行尾遮罩和行地址推进；
- `SysPartPicture`：左右位移两种公共字节行循环；
- `SysChinese` / `SysAscii`：字形行计算与多行批处理；
- `SysLine` / `SysRect`：坐标到 LCD 地址换算，以及掩码、别名选择、置位或
  清位组成的完整逐像素尾链；
- `SysFillRect` 和局部清屏：整字节横向填充循环，边缘像素复用上述像素尾链。

这些路径都按当前 `s6502_exec()` 剩余周期预算分批执行，预算不足时不修改状态并
回退 AOT/解释器，因而不会跨过 Timer/IRQ 调度边界。新增差分测试分别覆盖：
`SysPicture` 头部 3,000 组、LCD 地址换算 5,000 组、横向填充 3,000 组、
`SysPartPicture` 左右各 3,000 组、像素尾链 5,000 组；每组均比较完整 RAM、
CPU 寄存器和标志、栈、LCD dirty 状态及客机周期数。

## 后续候选

在完整画像中扣除现有静态 AOT 块后，普通字形、宽字形、直接存储器填充、
16 位乘法以及上述公共图片和图元链均已纳入 HLE。下一步应使用真机轻量日志
确认各公共路径的实际收益，再用完整诊断构建重新采样剩余热点；优先融合仍占据
较多整体耗时的公共调用者链，而不是继续堆叠单游戏短基本块。`$5C38-$5CB2`
的外层准备和 `$5D05-$5DCA` 的遮罩尾部每行调用次数较少，预计收益低于整段
调用者融合。
`$7233` 的零填充、`$8822` 的字节列指针换算以及 `$7C29` 乘法等独立例程
保留为候选。

## 真机评估

开启“性能调试”后，正常退出游戏会覆盖写入 `A:\gam4980\PERF.LOG`，其中包括：

```text
firmware_hle=1
firmware_hle_hits=...
firmware_hle_guest_cycles=...
firmware_hle_path0=... batch_groups=... batch_iterations=... batch_max=...
```

`firmware_hle_hits` 为快速路径命中次数；`firmware_hle_guest_cycles` 使用十六进制
记录被替代的客机周期总数。核心逐状态测试和 9288 指令级模拟器负责等价回归；
它们不能代表 S1C33 真机收益。性能回归只使用真机，在相同场景、相同设置下
对比帧率、操作响应和 `PERF.LOG`。`batch_iterations / batch_groups` 是每次进入
批量 HLE 实际完成的平均客机循环数，`batch_max` 是单次最大值。需要做基线比较
时可临时关闭 HLE。`direct_iterations / batch_iterations` 表示该路径批量迭代中
真正绕过通用内存分派的比例；当前日志只保留最近一次运行结果。

完整诊断日志会在 AOT/HLE/PC 采样等热路径维护大量计数，其中包括 S1C33 上
代价较高的 64 位累加。它用于找热点，不适合测发布版的绝对吞吐。需要确认这些
计数本身造成了多少减速时，应使用：

```text
build_9288.py --game-load-aot --lightweight-performance --optimization 2
```

轻量构建仍由设置页的“性能调试”开关决定是否写日志，但编译期移除了逐块、逐
HLE、PC 样本和 GUI tick 计数，只保留 RTC 墙钟、Timer 消息数、客机帧数、
提交帧数及 AOT/HLE 静态匹配数。日志头为 `[GAM4980 PERF LIGHT 1]`，并带有
`lightweight_benchmark=1`；它用来测接近发布版的真机速度，不能替代完整日志做
下一轮热点归因。两种构建必须分开采集和解释。
