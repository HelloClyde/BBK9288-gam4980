# BBK 9288 SDK 使用与兼容性问题

本文集中记录 `app_env_9288` 的实际用法、9288 V1.5 固件与公开头文件之间的
差异，以及开发下载应用时已经验证过的安全调用方式。它是 SDK 操作手册；完整的移植、
内存、性能和发布经验另见
[`9288-porting-lessons.md`](9288-porting-lessons.md)。

文中的结论分为三类：

- **已验证**：由 9288 SDK、官方 9288 EXE、9288 模拟器或真机共同确认。
- **固件兼容项**：只对当前使用的 9288 V1.5 固件确认，换固件必须重新验证。
- **未验证**：只有静态迹象，不应直接用于正式程序。

## 1. 最重要的规则

1. 只能使用 `app_env_9288`。9588、9288T 或其他机型的同名头文件、API 表和打包脚本
   都不能替代它。
2. SDK API 不是普通链接库函数，而是通过固件重定位表间接调用。必须先初始化
   `tpDL_GUITable`、`tpDL_FSTable` 等表指针。
3. 编译器必须实现 9288 使用的 GNU33 ABI：前四个参数走 R6–R9，返回值走 R4，
   R15 由加载器保留为应用数据基址。
4. SDK 成员名和结构偏移只能证明“公开头文件怎样定义”，不能证明当前固件相同位置
   仍实现相同 ABI。晚期、游戏、时钟和组合键 API 尤其需要核对官方程序。
5. 模拟器通过不等于真机兼容。私有槽位必须至少完成“官方 EXE 调用现场 + 模拟器最小
   程序”，高风险功能还要真机验证。

## 2. SDK 目录和构建方式

工程接受的 SDK 根目录结构至少包含：

```text
app_env_9288/
├── Down_Include/    C 头文件和各重定位表定义
└── apmk/            官方应用资源；本项目只从中复用 9288 图标框
```

SDK 不进入代码仓库，也不在 README 中提供其他机型 SDK 链接。推荐通过构建参数显式
指定，避免当前目录里残留的 9588 头文件被误用：

```bash
python3 build_9288.py \
  --sdk /path/to/app_env_9288 \
  --toolchain /path/to/piece-toolchain-llvm/build/bin
```

旧 SDK 头文件混用了 Windows 反斜杠路径和不一致的文件名大小写。本项目的
`prepare_sdk_headers()` 会将 `Down_Include` 复制到独立构建目录，并生成大小写兼容
副本。业务源码应包含生成后的头文件，不能直接修改 SDK 原件来“修好一次编译”。

构建必须至少使用这些目标约束：

```text
--target=s1c33-none-elf
-ffreestanding
-fno-builtin
-DDL_DOWN
-D_RLS_
```

工具链还必须应用仓库中的 `toolchain/9288-gnu33-abi.patch`。仅仅生成 S1C33 指令并不
代表 ABI 正确；错误 ABI 最常见的表现是简单无参 API 可运行，多参数 API 随机写内存或
直接重启。

## 3. 下载应用的启动和重定位表

### 3.1 入口不是普通 `main()`

9288 KF2 下载应用由加载器调用 `DL_AppMain(long argument)`。应用启动代码需要：

1. 清零真正的 `.bss`。
2. 从固定地址读取总重定位表。
3. 初始化各 SDK 表指针。
4. 最后进入业务 `App_Main()`。

公开 SDK 定义的总表地址是：

```c
#define SYS_GENERAL_RELOCATION_TABLE_ADDRESS 0x02000200
```

本项目使用的初始化方式如下：

```c
T_GUI_RelocationTable *tpDL_GUITable;
T_CRTL_RelocationTable *tpDL_CRTLTable;
T_FS_RelocationTable *tpDL_FSTable;
T_ROS33_RelocationTable *tpDL_ROS33Table;
T_Audio_RelocationTable *tpDL_AudioTable;
T_Dict_RelocationTable *tpDL_DictTable;

static void init_relocation_tables(void)
{
    T_GeneralRelocationTable *table =
        (T_GeneralRelocationTable *)SYS_GENERAL_RELOCATION_TABLE_ADDRESS;

    tpDL_ROS33Table =
        (T_ROS33_RelocationTable *)table->ROS33_RelocationAddress;
    tpDL_GUITable =
        (T_GUI_RelocationTable *)table->GUI_RelocationAddress;
    tpDL_FSTable =
        (T_FS_RelocationTable *)table->FS_RelocationAddress;
    tpDL_AudioTable =
        (T_Audio_RelocationTable *)table->Audio_RelocationAddress;
    tpDL_CRTLTable =
        (T_CRTL_RelocationTable *)table->CRTL_RelocationAddress;
    tpDL_DictTable =
        (T_Dict_RelocationTable *)table->Dict_RelocationAddress;
}
```

必须读取表中的地址，不能把某次模拟器观察到的 GUI 函数绝对地址写死。内核重编、固件
变化或加载布局变化都可能改变绝对地址。

### 3.2 `.bss` 必须清零，但大缓冲区不应放进去

C 语言要求未显式初始化的静态对象初值为零，而 9288 加载器不会替下载应用完整实现
这一语义，所以启动代码清零 `.bss` 是必要的。启动慢通常不是“清零行为多余”，而是把
帧缓冲、ROM cache 等每次都会完整覆盖的大数组错误放进了 `.bss`。

大缓冲区应放在项目的 `.scratch (NOLOAD)`，并在首次读取前完整写入。KF2 又只按平坦
payload 长度保留应用地址，因此 `.scratch` 后还需要文件支持的 payload tail；只添加
`.noinit` 或 `NOLOAD` 并不能保证真机不会覆盖那段地址。

## 4. SDK 宏到底怎样调用函数

SDK 中常见的写法：

```c
#define fnGUI_SetTimer (*tpDL_GUITable->SetTimer)
#define fs_fopen       (*tpDL_FSTable->fopen)
#define malloc         (*tpDL_CRTLTable->CRTL_malloc)
```

这些宏最终都是“从重定位表取函数指针，再按头文件声明调用”。因此一次 API 调用是否
正确同时依赖四件事：

- 表指针已初始化。
- 结构成员偏移与固件表一致。
- 函数原型与固件实现一致。
- 编译器遵守 GNU33 参数和返回值 ABI。

建议对关键公开成员保留编译期偏移检查：

```c
typedef char PublicSysBltFrameOffsetMustBe59c[
    __builtin_offsetof(T_GUI_RelocationTable, SysBltFrame) == 0x59c ? 1 : -1
];
```

这个检查只能发现“当前包含的头文件不是预期 SDK”，不能证明 `+0x59c` 就是当前固件
真正的 `SysBltFrame`。固件兼容偏移仍需单独处理。

## 5. `GetCurrDateTime`：公开声明在 V1.5 上不兼容

### 5.1 问题表现

公开 `app_env_9288` 声明：

```c
void fnGUI_GetCurrDateTime(TimeInfo *timeinfo, DateInfo *dateinfo);
```

该成员在公开 GUI 表中的偏移是 `+0x57c`。按头文件正确传入两个结构指针后，模拟器和
真机都能从调用中返回，但 `TimeInfo`、`DateInfo` 仍全部为零。问题不在结构体是否清零，
也不在参数先后顺序，而是当前 9288 V1.5 固件的该槽位没有实现这套双结构输出 ABI。

不要通过交换两个指针、取消初始化或调用 `InitSystemRTC_Clock()` 猜测修复。这些做法
无法把错误的表槽和函数签名变成正确 ABI。

### 5.2 官方程序的真实调用

反汇编 NAND 中官方“时间.exe”后确认，它从 GUI 表 `+0x590` 取函数，传入六个输出
指针。顺序为：

```text
秒、分、时、日、月、年
```

固件兼容声明：

```c
#define BBK9288_V15_GET_RTC6_OFFSET 0x590u

typedef void (*Bbk9288V15GetRtc6)(
    u8 *second,
    u8 *minute,
    u8 *hour,
    u16 *day,
    u16 *month,
    u16 *year
);

static void get_rtc(
    u8 *second, u8 *minute, u8 *hour,
    u16 *day, u16 *month, u16 *year
)
{
    Bbk9288V15GetRtc6 function = *(Bbk9288V15GetRtc6 *)(void *)(
        (u8 *)(void *)tpDL_GUITable + BBK9288_V15_GET_RTC6_OFFSET
    );

    function(second, minute, hour, day, month, year);
}
```

返回的 `year` 是完整年份，例如 `2005`，不是从 1900 开始的偏移；这个入口也不提供
毫秒字段。官方程序会根据自己的内部结构再做年份转换，不能把它机械解释成 SDK 的
`TimeInfo/DateInfo` 布局。

GAM4980 的加载诊断也使用这个六参数入口：在准备、读文件、HLE、CFG、AOT 和
存档阶段前后各取一次 RTC，并把差值写入 `load_*_rtc_elapsed_ms`。这些字段适合找出
耗时数秒的启动阶段，但 RTC 只有整秒分辨率，不能拿来比较短函数或驱动 60 Hz
客机调度。

### 5.3 验证证据

官方程序调用后的六项数据与其屏幕显示的 `00:01:xx`、`2005-10-01` 对应。独立的
9288 最小程序随后在模拟器中得到：

```text
timer_messages=400
expected_gui_ms=10000
rtc_start_time_ms=20000
rtc_end_time_ms=30000
rtc_elapsed_ms=10000
rtc_valid=1
```

检测源码位于 [`../tests/9288_rtc_timer_probe.c`](../tests/9288_rtc_timer_probe.c)，构建脚本
位于 [`../tests/build_9288_rtc_timer_probe.py`](../tests/build_9288_rtc_timer_probe.py)。

### 5.4 写时间接口仍不要使用

静态反汇编显示 `+0x58c` 很可能是与六字段 getter 配套的写入函数，但本项目没有在
真机执行修改系统日期这种有状态操作，因此它仍属于**未验证**接口。公开 SDK 的
`fnGUI_SetCurrDateTime` 也不能因为名字相邻就直接调用。除非完成官方调用现场、参数范围、
返回状态和真机恢复方案验证，否则应用不应修改系统 RTC。

## 6. GUI Timer 和计时 API

### 6.1 正式调度使用 `SetTimer` 和 `MSG_TIMER`

已验证的应用主循环方式：

```c
#define TIMER_ID 1
#define TIMER_SPEED 1

fnGUI_SetTimer(window, TIMER_ID, TIMER_SPEED);

/* WindowProc */
case MSG_TIMER:
    frame_pending = 1;
    return 0;
```

退出时调用：

```c
fnGUI_KillTimer(window, TIMER_ID);
```

`speed` 表示固件系统 tick 数，不是毫秒。当前真机和探针结果表明一个 tick 约为
24.9 ms，`speed 1` 大约产生 40 次消息/秒；`speed 20` 接近 0.5 秒一次，而不是
20 ms。事件泵繁忙时还可能合并或延后 Timer 消息，因此它适合调度，不应被当作高精度
墙钟。

`MSG_TIMER` 中只设置 pending 标志，重计算放在消息派发返回后。已经消费的 Timer 消息
应直接返回 0，不再传给 `DefaultMainWinProc`，避免额外刷新。

### 6.2 区分三类“tick”接口

- `fnGUI_GetTickCount()`：可用于短区间性能差值，但计数单位应记录为 tick，不能直接
  标成毫秒。本项目将它用于性能日志和短接受延迟。
- `TickTimerOpen/TickGetCount/TickTimerClose`：是另一套需要显式生命周期的接口；没有
  完成真机兼容验证，不用于正式事件循环。
- ROS33 `get_tim`：属于操作系统时间服务，不等同于 GUI Timer，也不能仅凭函数名假设
  单位或下载应用调用上下文。

需要墙钟秒数时使用已验证的 V1.5 RTC 六字段入口；需要应用调度时使用 GUI
`MSG_TIMER`。不要让一个未经验证的 tick API 同时承担两种职责。

## 7. 窗口、消息循环和退出顺序

最小主窗口创建流程：

1. 清零 `T_GUI_MainWinCreate`。
2. 填写窗口过程、坐标、背景色和 `HWND_DESKTOP`。
3. `CreateMainWindow`、`ShowWindow`、`SetActiveWindow`、`SetFocus`。
4. 使用 `GetMessage`、`TranslateMessage`、`DispatchMessage` 处理消息。

关闭窗口时遵循 SDK 示例的生命周期：

```text
PostMessage(MSG_CLOSE)
  → WindowProc(MSG_CLOSE)
    → KillTimer
    → ReleaseDC
    → DestroyMainWindow
    → PostQuitMessage
  → GetMessage(&message, window) 消费该窗口的 Quit
  → ThrowAwayMessages(window)
  → MainWindowCleanup(window)
```

关闭阶段必须使用 `GetMessage(&message, window)`，不要改成全局
`GetMessage(&message, 0)`。后者可能提前消费桌面或加载器消息，造成退出后只剩底栏、
图标区没有恢复或直接卡住。

## 8. 屏幕输出和晚期 GUI 表偏移

公开 SDK 的 `SysBltFrame` 位于 GUI 表 `+0x59c`。当前 9288 V1.5 固件在晚期游戏 API
块前多了五个私有表项，官方程序对应的真实槽位是 `+0x5b0`。

固件兼容调用：

```c
#define BBK9288_V15_SYS_BLT_FRAME_OFFSET 0x5b0u

typedef void (*Bbk9288V15SysBltFrame)(
    T_GUI_HDC hdc,
    unsigned char *virtual_screen
);

Bbk9288V15SysBltFrame blit = *(Bbk9288V15SysBltFrame *)(void *)(
    (u8 *)(void *)tpDL_GUITable + BBK9288_V15_SYS_BLT_FRAME_OFFSET
);

blit(client_dc, virtual_screen);
fnGUI_InvalidateRect(window, 0, FALSE);
```

完整提交顺序来自官方《雷霆战机》：

1. `GetClientDC` 取得有效 DC。
2. `SysBltFrame` 提交 `320 × 240 × 2 bpp = 0x4b00` 字节虚拟屏。
3. `InvalidateRect(window, NULL, FALSE)`。
4. `MSG_PAINT` 交给 `DefaultMainWinProc` 完成 GUI/LCD 传输。

不要在 `MSG_PAINT` 内再次提交帧，否则提交、失效、paint 会形成永久循环。也不要把
`+0x5b0` 推广成所有 9288 固件的固定 ABI；它必须与固件版本一起记录。

### 同步加载期间的状态页

创建窗口后立即执行文件读取、扫描或索引时，程序尚未进入正常消息循环。此时直接
`TextOut` 后调用 `InvalidateRect` 或 `UpdateWindow`，只能保证重绘请求已经入队，
不能保证真机 LCD 已经显示；耗时工作结束前用户仍可能只看到空白页。

9288 SDK 自带的 `downsample.c::WaitPainted` 说明同步流程仍应派发到一条真实
`MSG_PAINT`，但真机和固定停留模拟器探针进一步确认：在游戏正常消息循环启动前，
即使 `BeginPaint/TextOut/EndPaint` 或 `SysBltFrame` 已执行，LCD 仍可能保留上一个
文件选择窗口。也就是说，消息已经处理并不等于游戏 HSDMA 表面已经成为当前扫描面。

同一个官方 `downsample.c::ClearScreen` 给出了早期显示的可靠路径：`0x3c0000` 是
`320 × 240 × 2 bpp` 的物理视频内存，正好 4800 个 32 位字。同步 Loading 应先在
普通缓冲区完成整帧栅格化，派发 paint 后再用 volatile 32 位写复制到该地址。进入
游戏消息循环后必须停止直接写显存，恢复 `SysBltFrame → InvalidateRect →
MSG_PAINT`，避免与 HSDMA 争用。

### 真机帧输出路径对照实验

为了区分 GUI Timer 限速、`SysBltFrame` 成本和直接写物理显存的成本，编写了独立
真机探针。三条路径使用相同的两张预生成 `320 × 240 × 2 bpp` 整帧，测试循环中不做
图像生成，每阶段由已验证的 RTC 六字段入口计时 10 秒：

1. `SetTimer(speed=1) → MSG_TIMER → SysBltFrame → InvalidateRect → MSG_PAINT`。
2. 不使用 Timer；每次 `MSG_PAINT` 完成后立刻用同样的 SDK 路径提交下一帧。
3. 不使用 Timer；用 volatile 32 位循环把整帧直接复制到 `0x003c0000`。

探针源码位于
[`../tests/9288_frame_path_benchmark.c`](../tests/9288_frame_path_benchmark.c)，构建脚本位于
[`../tests/build_9288_frame_path_benchmark.py`](../tests/build_9288_frame_path_benchmark.py)，
日志覆盖写入 `A:\FRAMEBEN.LOG`。

第一版只比较 Timer 驱动 SDK 和无限速直接显存，真机得到：

```text
Timer + SDK: 402 submit / 402 paint / 10 s = 40.2 fps
直接显存:   2081 frame / 10 s = 208.1 fps
```

这个 `5.18×` 差值主要来自第一条路径被 25 ms Timer 限制，不能据此判断
`SysBltFrame` 比直接写显存慢。第二版加入“无 Timer 的连续 SDK”作为同调度基准，真机
原始结果为：

```text
[9288 FRAME PATH BENCH 2]
timer_sdk_messages=401
timer_sdk_submissions=401
timer_sdk_paints=401
timer_sdk_paint_millifps=40100
loop_sdk_submissions=2635
loop_sdk_paints=2635
loop_sdk_paint_millifps=263500
direct_frames=1681
direct_millifps=168100
direct_vs_loop_sdk_paint_x10=6
```

三条路径换算如下：

| 路径 | 真机吞吐 | 每整帧名义耗时 | 结论 |
|---|---:|---:|---|
| Timer + SDK | 40.1 fps | 24.94 ms | 由 GUI Timer 周期限制 |
| 连续 SDK | 263.5 fps | 3.80 ms | 正常游戏帧提交的最快路径 |
| 连续直接显存 | 168.1 fps | 5.95 ms | 只有连续 SDK 的 63.8% |

`direct_vs_loop_sdk_paint_x10=6` 表示约 `0.6×`，不是 6 倍。连续 SDK 的整帧吞吐比
直接 CPU 复制高约 56.8%；提交数与 paint 数完全相同，也没有观察到请求合并或丢失。
这与固件使用硬件传输面的现象一致，但该探针只证明端到端 API 吞吐，不能把
`MSG_PAINT` 次数解释为 LCD 面板真实刷新次数，也不能仅凭结果断言具体 DMA 实现。

工程结论：

- GUI `speed=1` 的周期确认为约 25 ms，即约 40 Hz。空载时 401 条消息全部得到处理；
  游戏中低于 40 条/秒通常是一次客机执行超过 25 ms，导致消息循环来不及继续派发，
  不是 Timer 单位错误。
- 正常游戏循环继续使用 `SysBltFrame → InvalidateRect → MSG_PAINT`。不要为了性能改成
  直接写 `0x003c0000`；后者只保留给游戏 HSDMA 表面尚未激活的同步 Loading 页面。
- 不能把“Timer + SDK”和“无限速直接显存”直接相除评价绘图 API。比较输出路径时必须
  去掉相同的调度上限，第二版的连续 SDK 与连续直接显存才是有效对照。
- GAM4980 的实测屏幕提交通常只有约 2～4 次/秒。即使按连续 SDK 的 3.80 ms/帧上界
  估算，宿主屏幕提交也只占约 0.8%～1.5% 的墙钟时间；当前主要瓶颈是客机执行和客机
  内部绘图代码，而不是 9288 的最终屏幕提交。客机位图/文字函数仍可通过 HLE 加速，
  但它和宿主 `SysBltFrame` 成本是两个不同层次的问题。

## 9. 键盘 API

普通下载应用使用窗口消息即可：

```text
MSG_KEYDOWN
MSG_KEYUP
LOUHWORD(wparam) 取得扫描码
```

完整键盘不意味着所有名字带 `Game` 或 `ScanKey` 的 SDK API 都能直接使用。
`fnGUI_ScanKeyForGameComboKeys` 在普通应用中曾造成模拟器和真机卡死/重启，可能依赖
官方游戏框架的私有初始化，因此不再调用。

按键状态应由 `KEYDOWN/KEYUP` 成对维护。启动应用的 Enter 还可能保持按下，文件选择器
需要等待一次新的按下和释放，不能把桌面启动键穿透到下一个窗口。

## 10. 文件系统和内存 API

### 10.1 文件系统

9288 路径使用盘符和反斜杠，例如：

```text
A:\gam4980\伏魔记.gam
```

中文文件名按 GBK 处理。使用 `fs_fopen/fs_fread/fs_fwrite/fs_fseek/fs_fclose` 时必须
检查短读、短写和 seek 结果。保存流程使用 `fwrite`、`fs_update`、`fclose` 即可；普通
应用不要额外调用全局 `fs_flush_cache()`，它在模拟器中会破坏随后桌面恢复，而且不能
替代正确的文件关闭。

### 10.2 `malloc` 上限

SDK 的 `malloc/free` 实际调用 CRTL 重定位表。9288 虽有 8 MiB SDRAM，但固件、GUI、
应用映像和堆共享空间，真机能可靠取得的最大连续块约为 1.5 MiB。这个数字是保守工程
边界，不是 SDK 保证。

因此所有大分配都必须检查失败；不要一次申请两片 2 MiB ROM，也不要根据模拟器成功
推断真机有相同连续堆。优先使用静态 scratch、分页缓存和按实际文件大小分配。

### 10.3 S1C33L05 内部 RAM 执行与系统恢复

9288 的 S1C33L05 内置 16 KiB RAM，物理地址为 `0x00000000-0x00003fff`。KF2
应用则从外部内存 `0x02700000` 一带运行。因此，把短小热点代码复制进内部 RAM
执行，避开外部 SDRAM 取指等待，是一个有硬件依据的优化方向。这里的“内部 RAM
更快”已经确认；“所有访问严格零等待”以及某段真实代码的具体加速比例仍须以真机
对照实验为准，不能把“零等待”进一步解释为每条指令只需一个 CPU 周期。

9288 SDK 本身保留了内部代码段约定：

```ld
.iram 0x800 : AT(0x2700100)
```

即内部执行地址为 `0x00000800`，代码镜像位于应用映像的 `0x02700100`。链接脚本又
把普通 `.text` 放在 `0x02701800`，两者之间形成 `0x1700` 字节的镜像间隔。这个布局
能证明 SDK 设计过 IRAM 代码覆盖，但不能单独证明 `0x800-0x1eff` 在所有固件状态下
都可由普通应用长期独占。

内部 RAM 是系统共享资源，不是应用私有 scratch：

- SDK 把闹钟、输入法、电源等系统变量放在 `0x3fc0` 开始的位置。
- `0x3ffc-0x3fff` 被注释为内存签名。
- `gAmrResidentFlag` 的 SDK 注释明确写着“判断当前 IRAM 中是否存在 AMR 代码”，
  说明音频代码也会动态驻留于 IRAM。
- 开发环境的 `test_tpl/test_spl` 示例会关闭全局及外设中断、把 TTBR 指回
  `0x00c00000`，然后把代码复制到 `0x00000000` 或 `0x00000200` 跳转。这些示例
  属于接管机器的底层载荷入口，不是可直接照搬的、能够安全返回 GUI 的模板。

因此，“先备份 IRAM、覆盖并执行、退出前恢复”是合理且通常必要的做法，但还不充分。
正式实现至少必须满足：

1. 先通过固件、SDK 和真机探针确定精确覆盖范围；不要备份一段后就假定整个 16 KiB
   都可安全占用。
2. 复制、跳转和恢复代码本身必须在覆盖范围之外执行，栈也不能位于将被覆盖的区域。
3. 覆盖期间若仍允许中断，必须证明所有 ISR、陷阱向量及其数据都不使用该范围；否则
   应在一个有严格时长上限的原子窗口内屏蔽中断，或提供自己的完整中断处理环境。
4. 系统 IRAM 被替换期间不要调用 GUI、文件系统、音频、Timer 等 SDK API，因为这些
   API 可能依赖被覆盖的代码或数据。
5. 若修改 PSR、TTBR、中断使能、Timer、DMA、看门狗或 LCD 控制状态，退出时必须和
   RAM 一起逐项恢复。只恢复字节内容不能保证桌面可继续运行。
6. 恢复后对备份区做校验，并走正常窗口关闭流程。异常跳转、掉电或恢复中途失败都可能
   让系统挂起，因此第一次实验不能与正式播放器合并。

对 GAM4980 而言，完整解释器和整程序 AOT 代码远大于 16 KiB，不能整体搬入。更现实
的候选是紧凑的解释器分派内核、6502 状态更新内核或经过筛选的绘图/HLE 热核；客机
RAM、Flash 和图像数据仍位于外部内存，所以最终收益同时受外部数据访存限制。

### IRAM 与外部 RAM 真机对照探针

独立探针已经实现，源码位于
[`../tests/9288_iram_benchmark.c`](../tests/9288_iram_benchmark.c)，计算叶函数位于
[`../tests/9288_iram_benchmark_payload.c`](../tests/9288_iram_benchmark_payload.c)，构建脚本位于
[`../tests/build_9288_iram_benchmark.py`](../tests/build_9288_iram_benchmark.py)。它不与 GAM4980
播放器合并，只使用 `app_env_9288` 构建。

探针把同一段 68 字节、无重定位、无全局引用、无 SDK 调用的 S1C33 叶函数分别放到：

- `.scratch` 中的外部可执行 RAM，地址约为 `0x027...`。
- SDK `.iram` 约定的起点 `0x00000800`。

正式真机版执行 `16384 × 1024 = 16777216` 次计算迭代。每个短批次都执行同一套原子
包装：

```text
读取并保存 PSR
→ 清 PSR.IE，屏蔽可屏蔽中断
→ 把 68 字节叶函数复制到目标地址
→ 执行 1024 次计算迭代
→ 把目标地址原内容逐字节恢复
→ 原样写回 PSR
```

外部 RAM 和 IRAM 阶段都包含相同的复制、调用、恢复和 PSR 切换开销，避免把两条路径
测成不同工作负载。每个批次恢复 PSR 后，待处理的系统中断有机会执行；不会连续数秒
关闭中断。覆盖期间执行的包装代码、栈、原始代码和备份均位于外部内存。

运行前探针还会：

1. 检查 `0x3fca` 的 `gAmrResidentFlag`；非零立即中止，不写 IRAM。
2. 读取 SP，若离 `0x800` 测试范围过近则中止。
3. 备份 `0x800` 开始的原始 68 字节并计算哈希。
4. 先执行一次只写入、不执行的写入/读回/恢复预检。
5. 明确显示风险确认框；取消后不执行实验。

结束后会比较外部和 IRAM 的计算结果，逐字节检查 IRAM 恢复，检查 PSR 的 IE/IL 控制位、
内存映射的 TTBR 寄存器和 AMR 标志没有变化，并把完整结果覆盖写入
`A:\IRAMBEN.LOG`。关键性能字段如下：

```text
external_ticks / iram_ticks
external_rtc_elapsed_ms / iram_rtc_elapsed_ms
tick_speed_x100 / rtc_speed_x100
iram_restored / state_restored / result
```

`speed_x100=100` 表示持平，`200` 表示 IRAM 阶段约为外部 RAM 的 2 倍。RTC 只有整秒
分辨率，以较细的非零 tick 比值为主，RTC 比值和人工秒表用于交叉检查。

缩短为 `8 × 64` 的模拟器等价测试已经通过：两段代码结果一致、IRAM 原字节哈希一致，
PSR/TTBR/AMR 检查通过并能显示结果页。不过模拟器不能提供真实存储器等待状态，性能
结论必须来自真机。

2026-08-29 的 9288 真机正式测试结果如下：

```text
total_kernel_iterations=16777216
external_rtc_elapsed_ms=35000
iram_rtc_elapsed_ms=8000
external_result=F7980612
iram_result=F7980612
rtc_speed_x100=437
iram_restored=1
state_restored=1
result=PASS
```

因此，在这个 68 字节、以寄存器运算为主的相同叶函数上，从外部 RAM 取指改为 IRAM
取指带来了约 `4.37×` 加速。折算平均时间约为外部 RAM `2.09 us/次`、IRAM
`0.48 us/次`。两段测试分别持续 35 秒和 8 秒，RTC 的 1 秒量化不足以推翻倍数级差异。
真机的 `TickGetCount()` 在两段中仍然返回零，因此这里以 RTC 长时间测量为准。

测试后的计算结果一致，`0x800-0x843` 原始哈希恢复一致，SP、TTBR、AMR 未变化，
PSR 只出现普通算术条件标志差异，IE/IL 控制位恢复正常。这确认了两件事：

1. 9288 上外部 RAM 取指等待是 GAM4980 性能的重要限制之一。
2. SDK 约定的 IRAM 覆盖方向值得进入播放器实验，但整体加速不会直接等于 `4.37×`，
   因为客机 RAM/Flash 数据访问和未迁移的 AOT 代码仍在外部内存。

`GAM4980 IRAM 热核` 严格采用 SDK 的 `.iram 0x800 : AT(0x2700100)` 布局，容量限制为
`0x1700` 字节，只迁入已做等价验证的图片大块 HLE：位图矩形、移位绘制、图片入口和
公共行尾。

模拟器验证否定了“应用启动时安装、退出时恢复”的常驻覆盖方案：应用恢复中断后，固件
会继续改写同一段 IRAM；稍后调用热核时，取指已经不是刚安装的代码。模拟器在第一次
图片 HLE 入口准确捕获到 `pc=0x02000802` 的旧半字，证明数据读回校验通过也不能保证
系统会把该范围长期留给应用。

因此正式实验改成和独立真机探针相同的**逐次瞬时覆盖**：每次调用一个热函数前检查
`gAmrResidentFlag`，关闭中断，只备份该函数实际占用的 IRAM 子区，按字节复制并校验，
立即调用；函数返回后仍在同一原子窗口内恢复并逐字节校验，最后才恢复 PSR。四个函数
分属独立 linker 子区，不需要为一次调用复制完整 `0x1700`。若音频暂时占用 IRAM，
只跳过本次热核调用并回退原来的 AOT/解释路径，下一次继续尝试；复制或恢复失败才停止
后续覆盖。这样桌面启动按键音不会导致整个播放器拒绝启动，也不会覆盖 AMR。

`PERF.LOG` 增加：

```text
iram_hot_core_enabled
iram_hot_core_size
iram_hot_core_restored
iram_hot_core_status
iram_hot_core_calls
iram_hot_core_bytes_installed
```

独立探针只直接证明 `0x800-0x843` 在“每批关中断、立即恢复”的短覆盖模型中可用，
不能证明更大子区也安全，更不能证明 `0x800-0x1eff` 可长期独占。播放器实验还必须用
模拟器完成画面/状态等价回归，再由真机确认中断延迟、性能、正常退出和返回桌面；只有
这些全部通过后，才考虑迁入紧凑解释器分派等更高频热核。

### GAM4980 IRAM 热核第一版结果

2026-08-29 的第一版最终链接映像为 `5832` 字节，仍在 SDK 的 `0x1700 = 5888`
字节上限内，余 `56` 字节。四个独立瞬时覆盖子区为：

| 热函数 | IRAM 范围 | 代码大小 |
|---|---:|---:|
| 图片入口 | `0x0800-0x0b9d` | 926 B |
| 图片公共行尾 | `0x0ba0-0x1105` | 1382 B |
| 移位区域 | `0x1108-0x17db` | 1748 B |
| 位图区域 | `0x17dc-0x1ec5` | 1770 B |

实现过程中确认了两个不能只靠“复制后读回一致”发现的 S1C33 取指陷阱：

1. 外部 wrapper 用链接器生成的直接 `call` 跳到低地址 IRAM 时，模拟器会继续命中旧的
   `$0800` 翻译块；改成与真机探针一致的运行时地址 `call.d %rN` 后才能可靠进入新代码。
2. IRAM 热函数内部不能用相对 `call` 直接调用 `0x027...` 外部 helper。第一次真实跟踪
   在 `$11e0` 的 `s6502_firmware_hle_shift_row_cycles` 调用后跳到 `0x01000000`。
   最终版由外部 wrapper 把三个 helper 地址作为参数传入，IRAM 内全部使用寄存器调用。
   构建脚本会反汇编 `.iram`，发现任何带符号的直接 `call` 就拒绝产出 KF2。

正常配置的 9288 模拟器已经完成以下 HLE 开启等价回归：文件选择、标题菜单、新旅程、
开场文字、剧情对话、地图画面、短按退出以及长按退出返回桌面；退出 20 秒后桌面仍稳定。
此外，图片入口、图片公共行尾、移位区域和位图区域四组宿主端对照测试各执行 3000 个
样本，返回周期、6502 寄存器、标志位和完整内存状态均与原路径一致。
本次退出后从 NAND 读取的关键日志为：

```text
iram_hot_core_enabled=1
iram_hot_core_size=5832
iram_hot_core_restored=1
iram_hot_core_status=2
iram_hot_core_calls=14970
iram_hot_core_bytes_installed=24752008
```

这证明模拟器会真实进入热核并在 14970 次调用后全部恢复，而不是由于 AMR 忙一直回退。
同时，约 56 秒标题测试搬运了 24.75 MiB 函数映像；算上备份、安装、验证、恢复和再次
验证，真实内存流量更高。因此第一版仍是**真机性能实验版**，不能根据 IRAM 叶函数的
`4.37x` 直接宣称播放器更快。下一步必须用同一真机场景的 `PERF.LOG` 比较有效客机
帧率；若逐次搬运抵消收益，应改成按 GUI Timer/执行批次合并覆盖，而不能长期霸占 IRAM。

第一版随后在 9288 真机运行 205 秒，IRAM 安全状态通过，但确认出现性能回退：

```text
wall_guest_millifps=18321
wall_effective_speed_percent_x100=3053
iram_hot_core_status=2
iram_hot_core_restored=1
iram_hot_core_calls=8402
iram_hot_core_bytes_installed=13686274
```

同功能迁移前日志为 `20.154 fps / 33.59%`，第一版降至 `18.321 fps / 30.53%`，约慢
`9.1%`；Timer 消息率也从 `13.440 Hz` 同比例降至 `12.214 Hz`，所以回退来自每个执行
批次增加的工作量，不是 RTC 或 Timer 统计单位错误。8402 次覆盖平均每次安装约 1629
字节。按备份、安装、安装校验、恢复、恢复校验五轮计算，共遍历约 65.3 MiB；把每轮的
源和目标访问都计入，则约有 130.5 MiB 字节访问。结论是：IRAM 对已经驻留的叶函数有
明显优势，但对每次调用都临时搬运 1--2 KiB 的 HLE，搬运成本超过了执行收益。

第二版据此不再迁入短小的图片入口和单行公共尾部，只试验能一次处理多行的移位区域和
位图区域；在安装前先用外部只读估算器排除条件不符或当前周期预算不足的调用，并把复制
和逐字节校验合并为单轮。日志按四个区域分别记录安装、成功、条件回退和预算回退，供
真机继续筛除净收益为负的热核。

### 关中断裸机循环最小实验

为了验证“整个 GAM 会话期间停止固件调度、让 IRAM 热核常驻”是否可行，新增了独立的
高风险探针。源码为
[`../tests/9288_bare_loop_benchmark.c`](../tests/9288_bare_loop_benchmark.c)，构建脚本为
[`../tests/build_9288_bare_loop_benchmark.py`](../tests/build_9288_bare_loop_benchmark.py)，
模拟器驱动为
[`../tests/emulator_qmp_bare_loop_benchmark.py`](../tests/emulator_qmp_bare_loop_benchmark.py)。
它只使用 `app_env_9288`，不与 GAM4980 播放器合并。

从 9288 模拟器的板级实现、S1C33L05 寄存器布局和 V1.5 固件行为交叉确认了以下底层路径：

| 能力 | 地址/位 | 实验用途 |
|---|---:|---|
| Clock Timer 运行控制 | `0x00040151` bit 0 | 预检自由运行计数器已启动 |
| Clock Timer 256 Hz 二进制分频计数 | `0x00040153` | 完整 8 位硬件 Tick；32 Hz 只是 `TCD3` 位 |
| Clock Timer 秒至日 | `0x00040154-0x00040158` | 与分频计数组合成跨秒计数 |
| 中断使能 EIR | `0x00040270-0x00040279`、`0x000402a6` | 保存后清零，阻止固件 ISR 运行 |
| 中断因子 FIR | `0x00040280-0x00040289`、`0x000402a9` | 退出时只清除实验期间新增的 W1C 因子 |
| 键盘行选择 | `0x00300f46` | 8 行逐行低电平选通 |
| 键盘列输入 | K5 `0x000402c1`、P0 `0x000402d1` | 读取 7 列低电平按键状态 |
| 键盘方向控制 | `0x000402c0`、`0x000402d2` | 临时切换列线为输入并恢复 |
| 9288 物理退出键 | row 5、column 6 | 不经过 GUI 消息队列提前退出 |
| HSDMA | `0x00048220` 起、4 路、步长 `0x10` | 检查各通道 `+0x0c` bit 0 均为空闲 |
| LCD IVRAM | `0x003c0000` | 直接写 320×240、2-bpp、80 B/行帧缓冲 |
| TTBR | `0x00048134` | 前后只读校验映射未变化 |
| PSR.IE | `0x10` | 清零后进入关中断窗口，最后原样恢复 |

最小探针采取保守策略：Clock Timer 必须先通过活动预检；AMR 和全部 HSDMA 通道最多
等待 2 秒自然空闲，仍不空闲就拒绝接管，而不是在不知道传输所有权时强停活动通道。
确认框本身可能触发按键音，所以用户确认后还会再等待一次，并在清 PSR.IE 后做最后一次
不可竞争的检查；最后检查不通过时不写 IRAM。
用户确认后，它按下面顺序运行：

```text
保存 PSR、TTBR、EIR/FIR、键盘配置、0x800 IRAM 原字节和当前 LCD 帧
→ 清 PSR.IE，并清零所有 EIR
→ 安装 68 字节无重定位 IRAM 计算叶函数
→ 进入自有忙轮询循环
   ├─ 读取 0x40153-0x40158 的 256 Hz 硬件时间
   ├─ 直接扫描 8×7 键盘矩阵
   ├─ 每 8 个硬件 Tick（32 Hz）直接提交一帧到 0x3c0000
   └─ 连续从 0x800 执行常驻 IRAM 叶函数
→ 物理退出键或 2560 Tick（约 10 秒）后退出
→ 恢复 IRAM、LCD、键盘配置和中断因子/使能
→ 最后恢复 PSR，保存日志并返回桌面
```

关中断期间不调用 GUI、文件系统、音频、Timer 或其他 SDK API。`fnGUI_GetTickCount()`
只在进入和恢复之后各读一次，用于证明固件的 GUI Tick 在实验窗口内确实停止；实验计时
完全来自硬件 Clock Timer。IRAM 负载只安装一次，并在每个硬件 Tick 校验其 68 字节没有
被覆盖。

最初版本把 `0x40153` 错当成 0--31 的 32 Hz 数值，并只保留 `divider & 31`。
Epson 的 S1C33L05 原厂技术手册说明，该寄存器实际是由 256 Hz 输入驱动的完整 8 位
二进制计数器，`TCD0` 到 `TCD7` 分别输出 128 Hz 到 1 Hz；32 Hz 只是 `TCD3`，不是
整个寄存器的计数频率。手册见
[S1C33L05 Technical Manual](https://global.epson.com/products_and_drivers/semicon/pdf/id000276.pdf)
的 Clock Timer 章节。

这个错误在模拟器里没有暴露，因为当时的模拟器 Clock Timer 模型也把分频计数简化成了
32 Hz。真机首轮日志则出现：

```text

end_tick=1036769824
elapsed_ticks=4294967294
loop_iterations=7

```

这不是有效通过。真机的完整分频值继续向上计数时，其低 5 位从 2 跨到 0；旧代码把它
误认为时间倒退，再由无符号减法回绕成 `0xfffffffe`，仅运行 7 次就满足 320 Tick 的退出
条件。该结果作废。

`BARE LOOP BENCH 2` 已改为：读取完整 8 位 256 Hz 分频值；用日、时、分、秒和分频值
共同计算相对时间；完整复读时间字段避免跨秒撕裂；拒绝负值、超过 60 秒和非法日跳变；
超时阈值为 2560 Tick；日志增加起止日、日内秒、原始分频值、无效样本数、分频回绕数和
最大步长。即使读到不一致样本，也只会记为无效并继续运行，不会再由回绕误报成功。

### 裸机状态直接读取文件系统实验

2026-08-31 增加了 `BARE FS PROBE 1`。构建命令是在裸机探针构建脚本后加
`--fs-probe`；产物只用于独立实验，不合入播放器。实验先在正常固件状态创建一份确定的
4 KiB 数据文件，然后进入与上述实验相同的裸机状态：清 `PSR.IE`、屏蔽全部系统 IRQ、
安装常驻 IRAM 负载。此后不恢复固件调度，直接从外部 RAM 代码调用 9288 SDK 的
`fs_fopen/fs_fread/fs_fclose`，校验数据和关键机器状态，再继续运行裸机稳定性循环，最后
按标准路径恢复桌面。临时文件和日志只在恢复固件后写入或删除。

### GAM4980 会话级裸机实验版

真机 `BARE LOOP BENCH 2` 通过后，播放器增加了构建开关 `--bare-session`。该开关只允许
与 `--iram-hot-core` 和 `--lightweight-performance` 一起使用，避免把尚未完成真机性能
回归的底层路径误打进普通版本。会话结构为：

```text
GUI 完成文件选择、GAM/ROM 读取、AOT/HLE 匹配和首帧准备
→ 等待 AMR 与全部 HSDMA 通道空闲
→ 保存 PSR、TTBR、中断和键盘配置
→ 清 PSR.IE、屏蔽系统中断并再次检查后台状态
→ 用 256 Hz Clock Timer 驱动 60 Hz 客机帧
→ 直接扫描 8×7 键盘，直接写 0x3c0000 LCD 帧缓冲
→ 游戏退出或长按退出键
→ 恢复 IRAM、键盘、中断、TTBR/PSR
→ 返回 9288 桌面
```

两个 2 MiB 固件 BIN 不能全部常驻内存，播放器仍使用 32 页、每页 4 KiB 的 ROM 缓存。
现有播放器最初把“关中断时不能调用 SDK 文件系统”作为保守约束，因此缓存未命中使用
受控网关：先恢复 IRAM、键盘、中断和 PSR，调用 SDK 读一页，再等系统重新空闲并接管
机器。上面的 `BARE FS PROBE 1` 已在模拟器和真机证明只读补页不需要这次完整退出；后续
版本可以改成带状态复核的外部 RAM 直接读取。旧网关仍可保留为非裸机路径或异常回退，
但不能在已检测到关键状态损坏后盲目继续游戏。

最初实现试图一次复制和校验完整的 5832 字节 `.iram`。模拟器在整区校验时失败；68
字节探针本来也只证明了小范围可用，不能据此假定所有系统 IRAM 都可一次覆盖。正式实验
改为按函数懒安装：图片入口、公共行尾、移位区域和位图区域在每次接管后的第一次调用时
才备份、复制和校验，此后保持常驻；退出或 ROM 补页时只恢复实际覆盖过的函数范围。
这既消除了逐次 HLE 搬运，也不触碰未使用的 IRAM 区域。

ROM 补页恢复还暴露了一个真实竞态：第一次后台空闲检查发生在中断开启时，检查后到清
PSR.IE 之前，按键音任务可能重新占用 AMR。修正版在屏蔽中断后做不可竞争的第二次检查；
每次文件读取后也先走完整的有界空闲等待，再重新接管。

2026-08-29 的 9288 模拟器等价回归使用与真机相同内容的《伏魔记》，仅为绕过测试镜像
的中文 FAT 长文件名枚举问题而把镜像内文件名改为 `GAME.GAM`。验证结果如下：

- 裸机运行时采样到 `PSR=0`、`bare_status=ACTIVE`，CPU 位于播放器/IRAM 路径，不在
  固件 GUI Timer 循环。
- 标题阶段连续经历 124 次 ROM 缓存补页；第 125 次接管与第 125 次恢复全部成功，
  证明文件系统网关可重复往返，而不是只在第一次进入时碰巧工作。
- 直接矩阵扫描的确定键可跳过标题并进入“新的征程/再续前缘”菜单。
- 游戏自身退出后，IRAM 状态为 `RESTORED`、裸机状态为 `READY`，CPU 回到固件空闲
  PC `0x58`，PSR 恢复为 `0x10`，桌面显示和时钟正常。
- 另一次独立长按退出键测试同样回到娱乐分类桌面，验证了宿主强制退出路径。

这轮只证明功能等价和可恢复性，不代表性能已经达标。标题阶段约 124 次 ROM 补页说明
32 页缓存仍会频繁让出裸机所有权；真机性能日志必须新增并关注
`bare_rom_suspends`、`bare_entries/restores` 和有效客机帧率。若游戏深处持续抖动，下一步
应先减少补页次数（启动阶段预热、按固件调用图固定保留热页或在内存允许时扩大热点
缓存），而不是把关中断范围扩展到 SDK 文件 I/O。

### IRAM 执行微内核 A/B 实验

为了比较“把四个图形 HLE 放进 IRAM”和“把通用 6502 执行分派放进 IRAM”，另做了两
个互斥构建：A 版保留四个 IRAM 图形 HLE；B 版把这些 HLE 留在外部 RAM，将 IRAM 用于
通用 6502 指令微内核。B 版只在裸机会话有效，ROM 补页和退出时沿用同一套恢复协议。

B 版最终 `.iram` 为 `5684` 字节，占 SDK `5888` 字节上限的 `96.5%`，余 `204` 字节。
构建时的 IRAM 反汇编审计没有发现直接调用外部 RAM 的相对 `call`。宿主端以相同
《伏魔记》输入比较普通解释器与 IRAM 微内核，在 1、10、100、300、1000、3000 和
5000 客机帧处，CPU、RAM 和时间状态哈希均完全一致。实现中曾发现每执行 32 条直线
指令就返回 `_exit` 会额外触发 AOT/事件边界并造成时间状态漂移；修正版只在真实控制流
出口返回 `_exit`，普通批次直接回到解释器 `_next`。

9288 模拟器的同镜像 A/B 结果不支持把 B 版提升为正式版本：A 版约 80 秒已经进入
“新的征程/再续前缘”菜单，B 版仍处于白色启动阶段。B 版在这段时间内的计数为：

```text
iram_exec_calls=1091325
iram_exec_instructions=3084241
iram_exec_guest_cycles=9632436
iram_exec_zero_fallbacks=332133
iram_exec_control_exits=474504
```

平均每次跨区调用只执行 `2.83` 条客机指令，`30.4%` 的调用没有执行任何指令就回退，
另有 `43.5%` 因分支、调用或返回结束微内核批次。状态装入/写回、外部 wrapper、IRAM
间接调用、边界判断和回退成本因此远高于节省的外部 RAM 取指成本。模拟器不精确模拟
真机外部 RAM 等待状态，所以 B 版仍可用于真机 A/B 测量，但当前证据表明这种“每几条
6502 指令进出一次 IRAM”的结构不值得取代 A 版。

若继续迁移执行引擎，必须改成**会话级常驻、跨控制流连续执行**：一次进入后在 IRAM 内
持续运行到客机事件截止点，把寄存器和高频页指针留在局部变量中，只在 ROM 缺页、
硬件事件、HLE 边界或退出时返回外部 RAM；或者
在加载阶段生成能一次处理几十到几百条指令的编译器语义超级块。仅继续扩充 5.8 KiB
switch 微内核的 opcode 数量，无法消除当前最主要的跨区调用与短批次成本。

### IRAM 常驻解释循环 C 版

C 版按上面的结论重写，不再把分支、`JSR/JMP/RTS/RTI` 当作“微内核结束”。完整
65C02 通用循环、寻址、栈操作、控制流和直接 RAM 访问都位于同一个 IRAM 覆盖区；控制
转移完成后仍在 IRAM 内取下一条指令。只有以下边界才返回外部 RAM：

- 已到本次客机事件周期 deadline，或客机设置了 halt；
- 下一 PC 命中固件/游戏 HLE 分派位图，需要交给现有 HLE；
- 十进制 ADC/SBC、bank 寄存器、Flash/ROM 或其他有外部副作用的慢路径；
- ROM 缓存未命中，需要先完整恢复裸机会话再调用 SDK 文件系统。

IRAM 中的控制流仍使用原客机 PC、栈和逐指令周期数，不把整函数当成原子操作。周期
预算必须用饱和减法：`executed < cycles ? cycles - executed : 0`。旧实现直接做无符号
减法，在外部路径已经到达 deadline 时会回绕成巨大预算，让 IRAM 循环越过中断边界；
宿主长帧等价回归正是靠时间状态哈希发现了这个问题。

SDK 链接脚本理论上允许 5888 字节，但第一份 5880 字节常驻构建在真机启动 GAM 后只
留下白屏。它比此前真机实验触碰过的最大末地址多用了 48 字节，而且多出的部分恰好是
SBC 助手后半段。这个相关性还不能证明整段 IRAM 常驻已经安全，因此播放器暂时把 C、
链接脚本和构建器三处硬上限都收紧为 5832 字节，不允许构建悄悄漂回 SDK 理论边界。

循环继续使用同区 `noinline` 内存助手；NZ 和比较保持内联，二进制 ADC/SBC 则合并为
同一个加法助手：ADC 传原操作数，SBC 传按位取反的操作数。这样既保留 SBC 的 IRAM
执行，也比“删掉 SBC 后让编译器扩大主循环”的版本更小。目标反汇编审计会解析
`call/jp/jp.d` 的真实目标地址：内部助手跳转允许，任何从该区直接跳到外部 RAM 的目标
都会使构建失败。结束符号放在 4 字节对齐之后，保证最后一条 16 位 `ret` 所在的完整
取指单元也包含在安装和备份范围内。当前布局为：

```text
resident 65C02 loop       5126 bytes
IRAM memory/add helpers     582 bytes
session alignment             0 bytes
total                      5708 / 5832-byte experiment bound
spare to experiment bound    124 bytes
```

Page-0 的四个直接数据通道也有专门快路。通道物理地址小于 `0x8000` 时，读写、自动
递增、LCD dirty、`_PB` 和自动关机计数的特殊语义全部在 IRAM 内完成；若通道指向
Flash/ROM，则在修改地址寄存器之前退出，保证外部解释器只执行一次原始副作用。
`_ISR/_TISR` 的 W0C 清位写入同样直接完成；bank 选择和映射更新仍走完整慢路径。

宿主端用同一二进制分别关闭/开启 resident loop，验证结果为：

- 原始 `s6502_exec` 短切片 1、2、3、4、5、10、20、50、100、200、500、1000 次全等；
- 《伏魔记》《三国霸业6980-方案一》《魔塔之怀旧终曲》在 1、10、100、1000、5000
  客机帧处，CPU、RAM 与时间状态哈希全等；
- 构建只引用 `app_env_9288`，并同时检查 KF2、S1C33 ELF、IRAM 尺寸和跨区跳转。

2026-08-30 又在 `usb-connected=on` 的独立 9288 模拟器 NAND 上完成目标机回归。冷启动
的稳定自动化路径为：确认键退出日期提示、退出当前窗口、开始键回主菜单，再按 `9`、
`K`、确认进入文件选择并启动 `GAME.GAM`。运行期采样确认 resident 调用、指令和周期计数
持续增长，IRAM 状态为 `ACTIVE`，裸机状态为 `ACTIVE`；退出后 IRAM 为 `RESTORED`，
裸机为 `READY`，PC 回到固件空闲地址 `0x58`，PSR 为 `0x10`，TTBR 保持
`0x02000000`。QMP 的 F12 只是物理退出矩阵键的测试别名，繁忙宿主上单个脉冲可能恰好
落在两次裸机扫描之间，因此自动化使用至多三次有界长按；这不改变播放器逻辑。

裸机直接写 LCD 后，9288 启动器只会定时重画右下角时钟，不会发现图标区的物理显存已
被修改。`HWND_DESKTOP` 重画只能得到白色背景，而公开 SDK 中
`ShowStatusBarAndDesktop` 的成员位置又不等于 V1.5 固件真实槽位，不能猜偏移调用。
伪造 GUI 键盘消息不能可靠重建该页面。GDB remote 在真实物理数字 `9` 进入启动器
callback 时确认 `r7=0x11`、`r8=0x39`，即完整序列中确实包含
`MSG_KEYDOWN(scancode) → MSG_CHAR(ASCII) → MSG_KEYUP(scancode)`，且页面快捷键消费
`MSG_CHAR('9')`。但补齐三条 `SendMessage` 后仍然白屏，说明物理输入还先经过启动器的
全局键盘 hook/state；直接调用窗口 callback 并不等价。

最终方案在 `App_Main` 创建任何窗口前保存真实的 `0x3c0000` 页面。裸机会话退出后先
恢复系统，再按窗口过滤消费自己的 Quit 并完成 `MainWindowCleanup`，但此时只记录一次
待恢复请求，不立即改写 LCD。`App_Main` 必须先完成 IRAM 恢复、存档写入、性能日志和
缓冲区释放，再把启动器恢复作为返回固件前的最后一次操作；否则这些收尾工作期间积累的
GUI 传输仍可能在快照之后启动，把已经恢复的页面重新覆盖。

这里不能对启动器调用 `InvalidateRect`，也不能套用“必须等到启动器 `MSG_PAINT`”的旧
结论。旧诊断停在 restore stage 3，按启动器 HWND 共处理了 2326 条消息，全部都是
`MSG_TIMER`，从未收到 `MSG_PAINT`。这说明启动器并不知道应用曾绕过其 DC 直接修改物理
LCD；强制失效反而会在 V1.5 固件中安排一次较晚的白页传输，而且这次传输不会以该窗口
过滤器可见的 `MSG_PAINT` 形式出现。官方 `downsample.c::WaitPainted` 仍适合等待应用自己
刚创建窗口的首帧，但不能据此推导已存在启动器的退出恢复协议。

验证通过的退出同步流程是不失效启动器，重新激活已验证有效的启动器窗口和焦点后执行
两轮相同操作：每轮先按启动器 HWND 取得并派发一条普通消息，再用
`HavePendingMessage(launcher)` 只排空当时已经挂起的消息；随后有界等待全部 HSDMA 通道
空闲，并把保存的物理快照复制回 `0x3c0000`。第二轮的再次排队、空闲等待和快照复制会
覆盖第一轮之后才启动的迟到传输，因此最终写者仍是保存的桌面页面。两轮消息处理都必须
严格过滤到启动器 HWND，不能改用全局 `GetMessage`，也不能丢弃启动器消息或强行停止
HSDMA。

模拟器回归中，新流程退出后得到完整娱乐页；连续观察 10 秒，整屏只有右下角时钟区域的
15 个像素发生变化，证明启动器后台计时仍在正常重画，而图标区没有再被白页覆盖。退出后
CPU 状态也保持正确：PSR 为 `0x10`，TTBR 为 `0x02000000`，PC 回到固件空闲地址
`0x58`。

这里的宿主测试是等价回归，不是性能结论。模拟器可以验证驻留计数持续增长、ROM 网关
往返以及退出后 PSR/IRAM/GUI 恢复；外部 RAM 与 IRAM 的真实速度差仍必须由 9288 真机
的最新 PERF 日志判断。日志中的 `iram_exec_instructions / iram_exec_calls` 表示平均一次
跨区进入实际连续执行多少条客机指令；`zero_fallbacks`、`slow_exits`、`dispatch_exits`
和 `deadline_exits` 用于区分剩余开销来自慢寄存器、HLE 边界还是正常事件截止点。

真机白屏还暴露了一个诊断设计问题：不能把未初始化的客机 LCD 当作首帧提交，否则早期
取指故障看起来只像永久白屏。现在先展示最后一阶段 `STARTING GAME`，同步准备结束后再
把同一张纯白过渡帧同时提交给 `SysBltFrame` 和 `0x3c0000`，然后才进入裸机或 GUI
Timer 循环。这样不会把未初始化客机内存误当作画面，也不会让只局部刷新的游戏留下
Loading 文字；第一张真实客机更新会覆盖这张过渡帧。

## 11. 外部原生代码与 ROM cache 共用堆预算

真机 `malloc` 的可靠上限约为 1.5 MiB，不能在现有 Flash/Game 分配之外再追加一整套
原生代码。GAM4980 因此保持原来额外 512 KiB 的总预算不变，把它重新划分为：

```text
ROM bank cache       64 × 4 KiB = 256 KiB
native code arena                 256 KiB
合计                              512 KiB
```

ROM warm profile仍保留 116 页候选，但只装入能完整放下的范围；当前预热 92 页，
后续冷页由原有 LRU 和裸机文件系统 gateway 提供。不能为塞满 profile 而让整个预热
失败，也不能把大范围截成半段后误认为它已常驻。

原生 arena 使用四个等长槽。`GAM4980.NAT` 的 manifest 常驻 arena 前部，代码槽位于
其后；模块记录携带格式/ABI 版本、代码 hash、AOT 函数指纹和直接链接信息。构建器现将
固定 E.BIN 的 926 个已识别块全部编译成 20 个无重定位 S1C33 模块，而不是只打包热点。
当前包 ABI 为 4。IRAM 通过一次普通 C ABI 调用进入模块后，模块把 A/X/Y/SP/PC/P
保持在局部量/宿主寄存器中，并在同一“虚拟 4 KiB 窗口 + 物理 4 KiB bank”内直接链接
后续基本块；不会再为每个块保存、重载一次完整状态。deadline、关机、跨模块/HLE 和
bank 映射 epoch 是强制写回边界，因而不会跨过客机事件或在 bank callback 后继续使用
旧映射。`native_shared_blocks / native_shared_calls` 可量化一次桥接平均执行的块数，
`native_shared_chain_links` 与 `native_shared_max_chain` 分别记录省掉的中间桥接数和最长链。
固定分支/JSR/JMP 的同模块目标还会直接跳到目标标签，`native_shared_direct_links`
记录真实命中数。普通 RAM/ROM 读先使用 IRAM 已验证的 `page_kind + pages` 快路径；
写入使用模块内共享 helper，并完整保留 LCD dirty、PB、自动关机计数和 bank epoch
规则。模块入口不再假定为代码偏移 0，manifest 与每个页链接都会携带真实入口偏移。
启动预载一个公共模块，其余模块在 bank/PC 首次命中时读入并按 LRU 覆盖。模块尚未加载
或校验失败时，256 项 PC 页入口表对应项为零，IRAM 解释器继续执行原路径。因此磁盘上
可以保存完整的已知固件翻译结果，内存只保留当前工作集，而无需增加 IRAM；移除 KF2 中
重复的静态 AOT 后，正式 EXE 也由约 923 KiB 缩至约 669 KiB。

同一 loader 还支持格式 3 的同名 `<游戏名>.GNA`。这不是 9288 启动时 JIT：PC 端
生成器读取 GAM，按 C6502 的 16 KiB bank 布局恢复 `.bf_call` 入口和完整可证明
CFG，用 S1C33 LLVM 离线编译；真机只校验游戏大小、代码大小、入口和整文件 hash，
再按 PC 缺页加载对应模块。模块可按 2 KiB 编译组拆分以适应单槽大小，运行映射
仍按真实 4 KiB bank。GNA 同时携带实际翻译出的指令跨度；Flash 写入只有与这些
跨度重叠时才撤销全部游戏页入口并递增 mapping epoch，使当前原生链返回 IRAM。

裸机文件系统实验已经证明：在系统 IRQ handler 被抑制时，SDK 文件读取可保留 PSR、
TTBR、IRQ mask 和 IRAM 内容。模块 loader 仍在调用前使 IRAM residency 失效，调用后
重新安装并校验执行区；加载发生在 IRAM 已返回 C 的 bank 边界，绝不能在正在执行的
原生模块内部覆盖其槽。

部署时 `GAM4980.NAT` 与 EXE 放在同一个 `A:\gam4980` 目录；可选 GNA 与对应 GAM
同名并放在游戏目录。若 FAT 暴露的 GBK 长文件名与安装短名不一致，loader 还会尝试
`GAME.GNA` 兼容别名，并继续用完整游戏 hash 防止绑定错误。包缺失/损坏或 GNA 游戏
hash 不匹配属于性能降级，
不是功能错误；日志中的 `native_module_status=1`、`native_module_match_count=926`、
`native_module_preloaded>0` 才表示完整固件模块包已经验证并进入页分派表。

### 全量外部原生代码的真机否定结果

上述模块机制在模拟器中能正确运行并减少解释分派，但不能据此判断真机性能。一次覆盖
80 秒《伏魔记》会话的 9288 日志显示：格式 3 GNA 已成功绑定并实际执行
（`native_module_status=1`、`native_shared_calls=23767`），但只得到
`wall_guest_millifps=2562`、`wall_effective_speed_percent_x100=427`。同一阶段此前的
IRAM 执行核＋内置 AOT/HLE 约为 16～18 fps；全量外部原生版反而慢约 7 倍。

耗时归因排除了文件系统和屏幕：`bare_core_ticks=20358/20462`，核心占墙钟约 99.5%；
渲染和提交合计不到 0.5%，直接文件读取约 0.34%。会话中 163 个模块只常驻 7 个，发生
397 次加载、390 次淘汰，并从外部 SDRAM 执行约 4.49 MiB 的游戏原生代码。现有模拟器
没有准确模拟这种外部取指等待/大代码工作集代价，因此“模拟器更快”是错误的性能信号。

正式构建现在默认不定义 `GAM4980_DYNAMIC_NATIVE_ALL`：保留 5716 字节 IRAM 执行核、
内置固件 AOT 和 HLE，不打开 `.NAT/.GNA`，也不申请 256 KiB native arena。全量模块只
能通过 `--dynamic-native-all --native-game <file.gam>` 显式生成，用作实验，不再作为
真机默认路径。模拟器只负责等价回归；性能选择必须依赖真机 RTC 日志。

## 12. 常见问题速查

| 现象 | 常见原因 | 处理方式 |
|---|---|---|
| 编译成功，调用 API 后重启 | 混入 9588/9288T 表或工具链 ABI 错误 | 只复制 `app_env_9288`，先跑 ABI 最小探针 |
| API 返回但输出结构全零 | 公开成员与 V1.5 固件 ABI 不一致 | 查官方 EXE；RTC 使用已验证的 `+0x590` 六指针入口 |
| 调用偏移后白屏 | 猜错 GUI 私有槽位 | 同时核对表基址、偏移、寄存器参数和调用后序列 |
| 游戏画面不刷新 | 只复制虚拟屏，没有触发 GUI paint | `SysBltFrame` 后调用 `InvalidateRect` |
| Loading 仍显示上一个窗口或白屏 | 游戏 HSDMA 表面尚未激活 | 按官方 `downsample.c` 把 2-bpp Loading 帧写入 `0x3c0000` |
| CPU 满载且不断 paint | 在 `MSG_PAINT` 再次提交帧 | paint 交给 `DefaultMainWinProc` |
| Timer 比预期慢约 20 倍 | 把 `speed` 当成毫秒 | `speed` 是约 24.9 ms 的 tick 数，正式使用 1 |
| 模拟器正常，真机计时异常 | 使用主动 tick deadline 或假设单位 | 调度改用 `MSG_TIMER`，墙钟改用验证过的 RTC |
| 退出后桌面残缺 | 关闭时全局消费 Quit，或裸机直接写 LCD 后启动器未重建页面 | 关闭循环过滤到本窗口；清理完成后再让启动器处理有界页面切换/重绘 |
| 大文件加载时真机重启 | 连续 `malloc` 超过可靠堆空间 | 以约 1.5 MiB 为上限，改用分页缓存 |
| 启动白屏很久 | 大型数组放在 `.bss` | 只清零小状态，大缓冲放 `.scratch` |
| 组合键 API 一调用就卡住 | 缺少官方游戏框架私有状态 | 改用 `MSG_KEYDOWN/MSG_KEYUP` |
| IRAM 优化后退出即挂 | 覆盖了系统代码/数据，或只恢复 RAM 而未恢复中断和 TTBR | 先用独立探针确认范围；保存并恢复全部相关状态 |
| 裸机模式运行几秒后掉回错误框 | ROM 补页后未等待 AMR/DMA 空闲，或关中断前发生竞态 | 文件 I/O 后重新走空闲门控，清 PSR.IE 后再复核一次 |
| 整段 IRAM 校验失败 | 小范围探针不能证明整个 `.iram` 可覆盖 | 按已验证热函数子区懒安装，只恢复实际覆盖区 |
| 常驻 IRAM 版启动 GAM 后白屏 | 覆盖逼近 SDK 理论末端，或误提交未初始化客机 LCD | 收紧实验上限；对齐完整取指范围；只在准备结束后提交前端生成的纯白过渡帧 |
| 全量 GNA 在模拟器快、真机却降到约 4% 实时速度 | 模拟器未准确反映外部 SDRAM 取指和大代码工作集成本 | 真机默认使用 IRAM＋内置 AOT/HLE；GNA 仅保留为显式实验 |

## 13. 新 API 的验证流程

遇到未验证 SDK API 时，按以下顺序处理：

1. 在 `RT_*.h` 中记录公开成员偏移和声明，不先假定它正确。
2. 确认总重定位表和目标子表的运行时基址。
3. 从同固件官方 EXE 找调用现场，记录表偏移、R6–R9、栈参数、返回值和调用后用途。
4. 反汇编槽位指向的固件函数，确认它确实读写预期参数。
5. 编写只包含一个窗口和一次目标调用的最小 KF2。
6. 在独立 NAND 副本的模拟器中验证返回值、内存边界和退出。
7. 对内存、时间、文件系统和系统状态类 API 再做真机验证。
8. 把结论标成公开 SDK、固件兼容项或未验证，避免以后把推测当成 ABI。

私有兼容代码应集中定义偏移和函数原型，并附官方程序证据；业务代码中不要散落裸
`GUI+0x...`。换固件时只需集中复核这一层。
