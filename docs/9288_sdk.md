# BBK 9288 SDK 使用与兼容性问题

本文集中记录 `app_env_9288` 的实际用法、9288 V1.5 固件与公开头文件之间的
差异，以及开发下载应用时已经验证过的安全调用方式。它是 SDK 操作手册；完整的移植、
内存、性能和发布经验另见
[`9288-porting-lessons.md`](9288-porting-lessons.md)。

文中的结论分为三类：

- **已验证**：由 9288 SDK、官方 9288 EXE、9288 模拟器或真机共同确认。
- **固件兼容项**：只对当前使用的 9288 V1.5 固件确认，换固件必须重新验证。
- **未验证**：只有静态迹象，不应直接用于正式程序。

## 1. 最重要的规则

1. 只能使用 `app_env_9288`。9588、9288T 或其他机型的同名头文件、API 表和打包脚本
   都不能替代它。
2. SDK API 不是普通链接库函数，而是通过固件重定位表间接调用。必须先初始化
   `tpDL_GUITable`、`tpDL_FSTable` 等表指针。
3. 编译器必须实现 9288 使用的 GNU33 ABI：前四个参数走 R6–R9，返回值走 R4，
   R15 由加载器保留为应用数据基址。
4. SDK 成员名和结构偏移只能证明“公开头文件怎样定义”，不能证明当前固件相同位置
   仍实现相同 ABI。晚期、游戏、时钟和组合键 API 尤其需要核对官方程序。
5. 模拟器通过不等于真机兼容。私有槽位必须至少完成“官方 EXE 调用现场 + 模拟器最小
   程序”，高风险功能还要真机验证。

## 2. SDK 目录和构建方式

工程接受的 SDK 根目录结构至少包含：

```text
app_env_9288/
├── Down_Include/    C 头文件和各重定位表定义
└── apmk/            官方应用资源；本项目只从中复用 9288 图标框
```

SDK 不进入代码仓库，也不在 README 中提供其他机型 SDK 链接。推荐通过构建参数显式
指定，避免当前目录里残留的 9588 头文件被误用：

```bash
python3 build_9288.py \
  --sdk /path/to/app_env_9288 \
  --toolchain /path/to/piece-toolchain-llvm/build/bin
```

旧 SDK 头文件混用了 Windows 反斜杠路径和不一致的文件名大小写。本项目的
`prepare_sdk_headers()` 会将 `Down_Include` 复制到独立构建目录，并生成大小写兼容
副本。业务源码应包含生成后的头文件，不能直接修改 SDK 原件来“修好一次编译”。

构建必须至少使用这些目标约束：

```text
--target=s1c33-none-elf
-ffreestanding
-fno-builtin
-DDL_DOWN
-D_RLS_
```

工具链还必须应用仓库中的 `toolchain/9288-gnu33-abi.patch`。仅仅生成 S1C33 指令并不
代表 ABI 正确；错误 ABI 最常见的表现是简单无参 API 可运行，多参数 API 随机写内存或
直接重启。

## 3. 下载应用的启动和重定位表

### 3.1 入口不是普通 `main()`

9288 KF2 下载应用由加载器调用 `DL_AppMain(long argument)`。应用启动代码需要：

1. 清零真正的 `.bss`。
2. 从固定地址读取总重定位表。
3. 初始化各 SDK 表指针。
4. 最后进入业务 `App_Main()`。

公开 SDK 定义的总表地址是：

```c
#define SYS_GENERAL_RELOCATION_TABLE_ADDRESS 0x02000200
```

本项目使用的初始化方式如下：

```c
T_GUI_RelocationTable *tpDL_GUITable;
T_CRTL_RelocationTable *tpDL_CRTLTable;
T_FS_RelocationTable *tpDL_FSTable;
T_ROS33_RelocationTable *tpDL_ROS33Table;
T_Audio_RelocationTable *tpDL_AudioTable;
T_Dict_RelocationTable *tpDL_DictTable;

static void init_relocation_tables(void)
{
    T_GeneralRelocationTable *table =
        (T_GeneralRelocationTable *)SYS_GENERAL_RELOCATION_TABLE_ADDRESS;

    tpDL_ROS33Table =
        (T_ROS33_RelocationTable *)table->ROS33_RelocationAddress;
    tpDL_GUITable =
        (T_GUI_RelocationTable *)table->GUI_RelocationAddress;
    tpDL_FSTable =
        (T_FS_RelocationTable *)table->FS_RelocationAddress;
    tpDL_AudioTable =
        (T_Audio_RelocationTable *)table->Audio_RelocationAddress;
    tpDL_CRTLTable =
        (T_CRTL_RelocationTable *)table->CRTL_RelocationAddress;
    tpDL_DictTable =
        (T_Dict_RelocationTable *)table->Dict_RelocationAddress;
}
```

必须读取表中的地址，不能把某次模拟器观察到的 GUI 函数绝对地址写死。内核重编、固件
变化或加载布局变化都可能改变绝对地址。

### 3.2 `.bss` 必须清零，但大缓冲区不应放进去

C 语言要求未显式初始化的静态对象初值为零，而 9288 加载器不会替下载应用完整实现
这一语义，所以启动代码清零 `.bss` 是必要的。启动慢通常不是“清零行为多余”，而是把
帧缓冲、ROM cache 等每次都会完整覆盖的大数组错误放进了 `.bss`。

大缓冲区应放在项目的 `.scratch (NOLOAD)`，并在首次读取前完整写入。KF2 又只按平坦
payload 长度保留应用地址，因此 `.scratch` 后还需要文件支持的 payload tail；只添加
`.noinit` 或 `NOLOAD` 并不能保证真机不会覆盖那段地址。

## 4. SDK 宏到底怎样调用函数

SDK 中常见的写法：

```c
#define fnGUI_SetTimer (*tpDL_GUITable->SetTimer)
#define fs_fopen       (*tpDL_FSTable->fopen)
#define malloc         (*tpDL_CRTLTable->CRTL_malloc)
```

这些宏最终都是“从重定位表取函数指针，再按头文件声明调用”。因此一次 API 调用是否
正确同时依赖四件事：

- 表指针已初始化。
- 结构成员偏移与固件表一致。
- 函数原型与固件实现一致。
- 编译器遵守 GNU33 参数和返回值 ABI。

建议对关键公开成员保留编译期偏移检查：

```c
typedef char PublicSysBltFrameOffsetMustBe59c[
    __builtin_offsetof(T_GUI_RelocationTable, SysBltFrame) == 0x59c ? 1 : -1
];
```

这个检查只能发现“当前包含的头文件不是预期 SDK”，不能证明 `+0x59c` 就是当前固件
真正的 `SysBltFrame`。固件兼容偏移仍需单独处理。

## 5. `GetCurrDateTime`：公开声明在 V1.5 上不兼容

### 5.1 问题表现

公开 `app_env_9288` 声明：

```c
void fnGUI_GetCurrDateTime(TimeInfo *timeinfo, DateInfo *dateinfo);
```

该成员在公开 GUI 表中的偏移是 `+0x57c`。按头文件正确传入两个结构指针后，模拟器和
真机都能从调用中返回，但 `TimeInfo`、`DateInfo` 仍全部为零。问题不在结构体是否清零，
也不在参数先后顺序，而是当前 9288 V1.5 固件的该槽位没有实现这套双结构输出 ABI。

不要通过交换两个指针、取消初始化或调用 `InitSystemRTC_Clock()` 猜测修复。这些做法
无法把错误的表槽和函数签名变成正确 ABI。

### 5.2 官方程序的真实调用

反汇编 NAND 中官方“时间.exe”后确认，它从 GUI 表 `+0x590` 取函数，传入六个输出
指针。顺序为：

```text
秒、分、时、日、月、年
```

固件兼容声明：

```c
#define BBK9288_V15_GET_RTC6_OFFSET 0x590u

typedef void (*Bbk9288V15GetRtc6)(
    u8 *second,
    u8 *minute,
    u8 *hour,
    u16 *day,
    u16 *month,
    u16 *year
);

static void get_rtc(
    u8 *second, u8 *minute, u8 *hour,
    u16 *day, u16 *month, u16 *year
)
{
    Bbk9288V15GetRtc6 function = *(Bbk9288V15GetRtc6 *)(void *)(
        (u8 *)(void *)tpDL_GUITable + BBK9288_V15_GET_RTC6_OFFSET
    );

    function(second, minute, hour, day, month, year);
}
```

返回的 `year` 是完整年份，例如 `2005`，不是从 1900 开始的偏移；这个入口也不提供
毫秒字段。官方程序会根据自己的内部结构再做年份转换，不能把它机械解释成 SDK 的
`TimeInfo/DateInfo` 布局。

GAM4980 的加载诊断也使用这个六参数入口：在准备、读文件、HLE、CFG、AOT 和
存档阶段前后各取一次 RTC，并把差值写入 `load_*_rtc_elapsed_ms`。这些字段适合找出
耗时数秒的启动阶段，但 RTC 只有整秒分辨率，不能拿来比较短函数或驱动 60 Hz
客机调度。

### 5.3 验证证据

官方程序调用后的六项数据与其屏幕显示的 `00:01:xx`、`2005-10-01` 对应。独立的
9288 最小程序随后在模拟器中得到：

```text
timer_messages=400
expected_gui_ms=10000
rtc_start_time_ms=20000
rtc_end_time_ms=30000
rtc_elapsed_ms=10000
rtc_valid=1
```

检测源码位于 [`../tests/9288_rtc_timer_probe.c`](../tests/9288_rtc_timer_probe.c)，构建脚本
位于 [`../tests/build_9288_rtc_timer_probe.py`](../tests/build_9288_rtc_timer_probe.py)。

### 5.4 写时间接口仍不要使用

静态反汇编显示 `+0x58c` 很可能是与六字段 getter 配套的写入函数，但本项目没有在
真机执行修改系统日期这种有状态操作，因此它仍属于**未验证**接口。公开 SDK 的
`fnGUI_SetCurrDateTime` 也不能因为名字相邻就直接调用。除非完成官方调用现场、参数范围、
返回状态和真机恢复方案验证，否则应用不应修改系统 RTC。

## 6. GUI Timer 和计时 API

### 6.1 正式调度使用 `SetTimer` 和 `MSG_TIMER`

已验证的应用主循环方式：

```c
#define TIMER_ID 1
#define TIMER_SPEED 1

fnGUI_SetTimer(window, TIMER_ID, TIMER_SPEED);

/* WindowProc */
case MSG_TIMER:
    frame_pending = 1;
    return 0;
```

退出时调用：

```c
fnGUI_KillTimer(window, TIMER_ID);
```

`speed` 表示固件系统 tick 数，不是毫秒。当前真机和探针结果表明一个 tick 约为
24.9 ms，`speed 1` 大约产生 40 次消息/秒；`speed 20` 接近 0.5 秒一次，而不是
20 ms。事件泵繁忙时还可能合并或延后 Timer 消息，因此它适合调度，不应被当作高精度
墙钟。

`MSG_TIMER` 中只设置 pending 标志，重计算放在消息派发返回后。已经消费的 Timer 消息
应直接返回 0，不再传给 `DefaultMainWinProc`，避免额外刷新。

### 6.2 区分三类“tick”接口

- `fnGUI_GetTickCount()`：可用于短区间性能差值，但计数单位应记录为 tick，不能直接
  标成毫秒。本项目将它用于性能日志和短接受延迟。
- `TickTimerOpen/TickGetCount/TickTimerClose`：是另一套需要显式生命周期的接口；没有
  完成真机兼容验证，不用于正式事件循环。
- ROS33 `get_tim`：属于操作系统时间服务，不等同于 GUI Timer，也不能仅凭函数名假设
  单位或下载应用调用上下文。

需要墙钟秒数时使用已验证的 V1.5 RTC 六字段入口；需要应用调度时使用 GUI
`MSG_TIMER`。不要让一个未经验证的 tick API 同时承担两种职责。

## 7. 窗口、消息循环和退出顺序

最小主窗口创建流程：

1. 清零 `T_GUI_MainWinCreate`。
2. 填写窗口过程、坐标、背景色和 `HWND_DESKTOP`。
3. `CreateMainWindow`、`ShowWindow`、`SetActiveWindow`、`SetFocus`。
4. 使用 `GetMessage`、`TranslateMessage`、`DispatchMessage` 处理消息。

关闭窗口时遵循 SDK 示例的生命周期：

```text
PostMessage(MSG_CLOSE)
  → WindowProc(MSG_CLOSE)
    → KillTimer
    → ReleaseDC
    → DestroyMainWindow
    → PostQuitMessage
  → GetMessage(&message, window) 消费该窗口的 Quit
  → ThrowAwayMessages(window)
  → MainWindowCleanup(window)
```

关闭阶段必须使用 `GetMessage(&message, window)`，不要改成全局
`GetMessage(&message, 0)`。后者可能提前消费桌面或加载器消息，造成退出后只剩底栏、
图标区没有恢复或直接卡住。

## 8. 屏幕输出和晚期 GUI 表偏移

公开 SDK 的 `SysBltFrame` 位于 GUI 表 `+0x59c`。当前 9288 V1.5 固件在晚期游戏 API
块前多了五个私有表项，官方程序对应的真实槽位是 `+0x5b0`。

固件兼容调用：

```c
#define BBK9288_V15_SYS_BLT_FRAME_OFFSET 0x5b0u

typedef void (*Bbk9288V15SysBltFrame)(
    T_GUI_HDC hdc,
    unsigned char *virtual_screen
);

Bbk9288V15SysBltFrame blit = *(Bbk9288V15SysBltFrame *)(void *)(
    (u8 *)(void *)tpDL_GUITable + BBK9288_V15_SYS_BLT_FRAME_OFFSET
);

blit(client_dc, virtual_screen);
fnGUI_InvalidateRect(window, 0, FALSE);
```

完整提交顺序来自官方《雷霆战机》：

1. `GetClientDC` 取得有效 DC。
2. `SysBltFrame` 提交 `320 × 240 × 2 bpp = 0x4b00` 字节虚拟屏。
3. `InvalidateRect(window, NULL, FALSE)`。
4. `MSG_PAINT` 交给 `DefaultMainWinProc` 完成 GUI/LCD 传输。

不要在 `MSG_PAINT` 内再次提交帧，否则提交、失效、paint 会形成永久循环。也不要把
`+0x5b0` 推广成所有 9288 固件的固定 ABI；它必须与固件版本一起记录。

### 同步加载期间的状态页

创建窗口后立即执行文件读取、扫描或索引时，程序尚未进入正常消息循环。此时直接
`TextOut` 后调用 `InvalidateRect` 或 `UpdateWindow`，只能保证重绘请求已经入队，
不能保证真机 LCD 已经显示；耗时工作结束前用户仍可能只看到空白页。

9288 SDK 自带的 `downsample.c::WaitPainted` 说明同步流程仍应派发到一条真实
`MSG_PAINT`，但真机和固定停留模拟器探针进一步确认：在游戏正常消息循环启动前，
即使 `BeginPaint/TextOut/EndPaint` 或 `SysBltFrame` 已执行，LCD 仍可能保留上一个
文件选择窗口。也就是说，消息已经处理并不等于游戏 HSDMA 表面已经成为当前扫描面。

同一个官方 `downsample.c::ClearScreen` 给出了早期显示的可靠路径：`0x3c0000` 是
`320 × 240 × 2 bpp` 的物理视频内存，正好 4800 个 32 位字。同步 Loading 应先在
普通缓冲区完成整帧栅格化，派发 paint 后再用 volatile 32 位写复制到该地址。进入
游戏消息循环后必须停止直接写显存，恢复 `SysBltFrame → InvalidateRect →
MSG_PAINT`，避免与 HSDMA 争用。

## 9. 键盘 API

普通下载应用使用窗口消息即可：

```text
MSG_KEYDOWN
MSG_KEYUP
LOUHWORD(wparam) 取得扫描码
```

完整键盘不意味着所有名字带 `Game` 或 `ScanKey` 的 SDK API 都能直接使用。
`fnGUI_ScanKeyForGameComboKeys` 在普通应用中曾造成模拟器和真机卡死/重启，可能依赖
官方游戏框架的私有初始化，因此不再调用。

按键状态应由 `KEYDOWN/KEYUP` 成对维护。启动应用的 Enter 还可能保持按下，文件选择器
需要等待一次新的按下和释放，不能把桌面启动键穿透到下一个窗口。

## 10. 文件系统和内存 API

### 10.1 文件系统

9288 路径使用盘符和反斜杠，例如：

```text
A:\gam4980\伏魔记.gam
```

中文文件名按 GBK 处理。使用 `fs_fopen/fs_fread/fs_fwrite/fs_fseek/fs_fclose` 时必须
检查短读、短写和 seek 结果。保存流程使用 `fwrite`、`fs_update`、`fclose` 即可；普通
应用不要额外调用全局 `fs_flush_cache()`，它在模拟器中会破坏随后桌面恢复，而且不能
替代正确的文件关闭。

### 10.2 `malloc` 上限

SDK 的 `malloc/free` 实际调用 CRTL 重定位表。9288 虽有 8 MiB SDRAM，但固件、GUI、
应用映像和堆共享空间，真机能可靠取得的最大连续块约为 1.5 MiB。这个数字是保守工程
边界，不是 SDK 保证。

因此所有大分配都必须检查失败；不要一次申请两片 2 MiB ROM，也不要根据模拟器成功
推断真机有相同连续堆。优先使用静态 scratch、分页缓存和按实际文件大小分配。

## 11. 常见问题速查

| 现象 | 常见原因 | 处理方式 |
|---|---|---|
| 编译成功，调用 API 后重启 | 混入 9588/9288T 表或工具链 ABI 错误 | 只复制 `app_env_9288`，先跑 ABI 最小探针 |
| API 返回但输出结构全零 | 公开成员与 V1.5 固件 ABI 不一致 | 查官方 EXE；RTC 使用已验证的 `+0x590` 六指针入口 |
| 调用偏移后白屏 | 猜错 GUI 私有槽位 | 同时核对表基址、偏移、寄存器参数和调用后序列 |
| 游戏画面不刷新 | 只复制虚拟屏，没有触发 GUI paint | `SysBltFrame` 后调用 `InvalidateRect` |
| Loading 仍显示上一个窗口或白屏 | 游戏 HSDMA 表面尚未激活 | 按官方 `downsample.c` 把 2-bpp Loading 帧写入 `0x3c0000` |
| CPU 满载且不断 paint | 在 `MSG_PAINT` 再次提交帧 | paint 交给 `DefaultMainWinProc` |
| Timer 比预期慢约 20 倍 | 把 `speed` 当成毫秒 | `speed` 是约 24.9 ms 的 tick 数，正式使用 1 |
| 模拟器正常，真机计时异常 | 使用主动 tick deadline 或假设单位 | 调度改用 `MSG_TIMER`，墙钟改用验证过的 RTC |
| 退出后桌面残缺 | 全局消费 Quit 或调用全局 flush | 关闭循环过滤到本窗口，按 SDK 顺序清理 |
| 大文件加载时真机重启 | 连续 `malloc` 超过可靠堆空间 | 以约 1.5 MiB 为上限，改用分页缓存 |
| 启动白屏很久 | 大型数组放在 `.bss` | 只清零小状态，大缓冲放 `.scratch` |
| 组合键 API 一调用就卡住 | 缺少官方游戏框架私有状态 | 改用 `MSG_KEYDOWN/MSG_KEYUP` |

## 12. 新 API 的验证流程

遇到未验证 SDK API 时，按以下顺序处理：

1. 在 `RT_*.h` 中记录公开成员偏移和声明，不先假定它正确。
2. 确认总重定位表和目标子表的运行时基址。
3. 从同固件官方 EXE 找调用现场，记录表偏移、R6–R9、栈参数、返回值和调用后用途。
4. 反汇编槽位指向的固件函数，确认它确实读写预期参数。
5. 编写只包含一个窗口和一次目标调用的最小 KF2。
6. 在独立 NAND 副本的模拟器中验证返回值、内存边界和退出。
7. 对内存、时间、文件系统和系统状态类 API 再做真机验证。
8. 把结论标成公开 SDK、固件兼容项或未验证，避免以后把推测当成 ABI。

私有兼容代码应集中定义偏移和函数原型，并附官方程序证据；业务代码中不要散落裸
`GUI+0x...`。换固件时只需集中复核这一层。

## 13. 当前已确认的兼容项
