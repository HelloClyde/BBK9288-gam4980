# GAM → BBK 9288 原生重编译器

## 状态（2026-09-05）

这是PC离线重编译器，不是旧GAM4980播放器的AOT构建开关。输出独立KF2，真机
不需要原始GAM、BIN或GNA模块。游戏数据压缩内嵌，启动时解压；游戏控制流已经在
PC上编译为S1C33 call/ret/分支。

目前仍是功能验证版，**不是已经完成全流程验证的发行版**。独立9288模拟器已确认
应用启动、主菜单、新游戏开场正文、文字滚动、地图显示和方向键移动。
窗口化修正版已验证“系统→结束游戏→主菜单→退出应用→数字键切换桌面分类”。
存读档已完成“保存两个槽位→移动到未保存位置→退出应用→重新启动→读取第二槽→
继续移动”的模拟器回归，恢复后的角色记录与保存时逐字节一致。战斗及完整剧情
尚未完成回归，也没有本原生版的真机性能结论，不作为全流程验证的正式发行版。
用户确认原版地图两侧也有残留，因此按原版行为保留，不再作为待修缺陷。
撤回针对两侧残留增加的启动LCD清理，不通过裁剪或遮盖改变原版显示。
240组基础绘图对照通过不等于游戏所有场景均已验证。

旧文档曾将早期908,897字节产物描述为通过地图/方向键验证，证据不足，此声明撤回。
仅显示菜单不能证明正常运行：LCD能在固件异常死循环后保留旧图。验证工具现在同时
检查CPU状态，以及RAM中加载的入口与当前KF2是否逐字节一致。

## 构建

可视化入口：`build/GAM-to-9288-Converter.exe`，支持设置名称、四灰阶图标、
输出路径及查看实时编译日志。详见 [界面使用说明](gam-converter-gui.md)。

```powershell
python tools/compile_gam_native_9288.py "D:\Downloads\伏魔记.gam"
```

默认SDK仅为 D:\Downloads\app_env_9288。需要仓库修正版本的S1C33 LLVM工具链。
输出build/9288/伏魔记-NATIVE.exe及同名ELF、map、report.json。
命令行默认共享中间目录，公共构建入口通过操作系统文件锁拒绝并行转换。
界面为每次转换分配独立工作目录，仍保留锁保护共享的启动状态生成步骤。
可使用 `--app-name`、`--icon`、`--work-dir` 指定名称、图标和工作目录。
输出先在工作目录完成，校验通过后才替换目标 EXE。

构建器拒绝超过1 MiB的KF2、超出应用RAM窗口的映像、未知适配入口，以及未恢复的
静态跨bank调用/switch描述。编译通过不等于游戏全流程通过。
生成的游戏产物包含原游戏资源，不自动加入源码仓库或release。

## 执行架构

1. 从GAM头、C6502调用模板、bank表及switch表恢复函数与控制流。
2. 将多条机器指令提升为16位运算、栈访问、指针操作等编译器语义。
3. 对重复表达式提取共享原生函数，避免逐基本块重复大段状态代码。
4. FAR调用直接调用原生目标，同时维护该函数读取常量所需的bank映射。
5. 原A系列系统API链接到9288原生C适配层；这些C函数也编译为S1C33机器码。

没有运行时opcode取指、逐指令分派、客机周期调度或解释器回退。
仍保留二进制语义所需的寄存器/标志及地址映射，不宣称已经还原完整C源码、完成
全程序SSA或消除了所有调用开销。源码switch/间接控制流的目标表只查找已编译的
原生地址，不是逐条执行6502指令。

共享寄存器约定：A=R4，X=R5，Y=R6，SP=R7，延迟N/Z=R8，P=R9，
软件栈指针=R10，RAM基址=R14。进入SDK/C层时切换为GNU33 ABI：
参数R6–R9，结果R4/R5，R15为宿主数据指针。构建前有ABI探针。

FIR0是写1清除，不能将保存值直接写回。只清除扫描新增的KEY0/KEY1位，保留原有
因子和无关端口中断。宿主LCD为320×240、2-bpp，物理地址0x003c0000。
不能将A系列1-bpp图片直接交给9288的2-bpp接口。

V1.5晚期GUI游戏函数块比公开SDK多五项。当前+0x14修正仅按此固件验证，不将其

### 存读档根因及验证

A系列 `STDLIB.H` 将 `strcmp` 声明为 `int`。原 E.BIN 的 bank 4 `$604F`
将首个不同字节的8位减法结果符号扩展到 `$20/$21`，而旧适配只调用 `return8`。
游戏随后读取的仍是旧16位临时值，因而把已有存档误判成不匹配：页面显示空档案，
再次存储还会重复创建文件。修复保留原ROM的差值、标志和A/Y返回约定，不仅返回
固定的-1/0/1。144组对照覆盖相等、前缀、中文GBK及高位字节。

之前把缺少 `FileType 0x17` 记录判断为主要原因不准确。正常存读档路径使用游戏
创建的 `0x09` 数据记录；本修复不伪造 `0x17`，不更改文件类型映射。

独立实例 `native-save-clean-v28` 从无存档NAND开始，第一、第二槽均显示“百草地”。
第二槽保存位置为 `(3,2)`，退出前未保存位置为 `(1,2)`；重启应用读取第二槽后，
`RAM[$198D:$198F]` 恢复为 `03 02`，整个25字节角色记录一致，错误变量 `$1937=0`，
方向键继续改变角色位置。证据保存在
`D:/Temp/bbk9288-native-validation/native-save-clean-v28/` 的截图及RAM转储中。

随后确认覆盖第二槽，正常返回可操作桌面，再结束测试QEMU进程。
`native-save-cold-v29` 从这份持久化NAND冷启动，经“再续前缘”读取第二槽；
25字节角色记录与覆盖后的保存状态完全一致，方向与第一次保存不同，确认读出的是
覆盖后的内容，而非旧记录或上一次进程RAM。冷启动证据位于同目录的该实例子目录。
这不是断电写入原子性测试，也不替代真机文件系统测试。

## 体积与性能口径

### IO-BLIT-1：原生运行库性能修订

本轮不改变游戏翻译代码，也不添加解释器。修改集中在原生输入、计时和绘图适配：

- `SysGetKey` 不再无条件等待GUI消息。即时输入来自有界键盘矩阵扫描，保存/恢复
  行选择、K5、PORT0和PSR，只清除扫描新增KEY因子；按下边沿只报一次，方向键才连发。
  GUI仍处理本应用窗口，只有 `GuiGetMsg` 的等待路径允许阻塞；未接管整机。
- 不采用“投递空消息后GetMessage”：V1.5会直接取出消息而不采集新按键，
  独立模拟器发现输入饥饿后已撤回。也不混合返回硬件边沿与后到GUI KEYDOWN，避免
  Enter/Exit被消费两次。
- 用已验证CTM的日期/时分秒与256 Hz分频合成连续计数，稳定采样防跨秒撕裂。
  当时将游戏Timer固定为6个硬件tick，虽然修正了查询次数计时和低8位回绕，仍然
  忽略了A系列API的周期参数。这是错误的适配，已由下文TIMER-BOX-1修正；
  6个tick现在只用于宿主画面刷新，不再定义游戏Timer周期。
- 位图及字模按目标字节移位、掩码合成；全跨度证明源不与LCD别名重叠后才走快速路径。
  重叠/未知来源保留原读取顺序；ROM单字节图片的特殊padding行为保持不变。
- 64项字模缓存复用SDK生成的字体；横线、填充、清除、反色按整字节处理。
- 2×输出使用256项转换表及对齐32位写。曾尝试只重写变化行，但系统测试出现
  静止菜单变白/残留，已撤回：GUI仍共用物理LCD，不能根据客机RAM未变断言宿主
  画面有效。每次提交完整画面，变化行比较只用于统计；不裁剪游戏两侧内容。

构建增加 `--output build/9288/伏魔记-NATIVE-IOBLIT.exe` 可保留旧存读档版作比较。
产物958,701字节，SHA256
`660efed736a2a4c5a042b01f705adb0b660d30e43750618bfdeb95400a28db29`。

正常退出原生应用后写 `a:\NATIVE.LOG`，每次覆盖旧日志。格式为
`[FUMO NATIVE PERF 1]` / `build=IO-BLIT-1`，`clock_hz=256`；`elapsed`及
`poll_ticks`、`wait_ticks`、`graphics_ticks`、`present_ticks`都以该硬件tick计数。
`wait_ticks`包含阻塞消息泵时间，不等于纯游戏计算。其余字段记录调用、变化行和字模
缓存命中。逐调用计时量化到约3.90625ms，短调用可能为0；剩余时间还包括未分类的

暂停QEMU时RTC继续走，跨暂停调用会使归因失真，因此调试会话日志只验证格式和写盘，

### TIMER-BOX-1：地图名消息框与A系列Timer语义修复

原生适配层的旧 `GuiMsgBox` 只绘制固定大框便立即返回，既没有采用超时参数，
也没有保存、恢复背景。因此地图名框过高、瞬间消失并非单纯帧率问题。
旧 `SysTimer1Open` 忽略参数、Close未真正停止、GetNumber返回运行计数，也均不符合ROM。
本轮仅修复原生运行库，不修改游戏代码，不添加运行时解释器。

原ROM对照证据：

- E.BIN bank 7 `$7B4C/$7B6F/$7B7D` 分别为Open/Close/GetNumber，`$7B8B`为IRQ计数。
  `SysTimer1Open(U8 times)` 的参数是每次消息累计的IRQ数，不是ST1LD重装值。
  零参数、重复Open为无操作，Close清开关，GetNumber返回已配置值，关闭时返回0。
- 原核心Timer源为4 MHz / 400 = 10 kHz；启动快照 `$0227=0xA6`，稳态每90个源tick
  产生一次IRQ（约9 ms）。开发包注释“百分之一秒”为近似单位，不能误当宿主25 ms
  GUI消息，或把游戏参数0xF2当硬件reload。首个计数相位及停止/恢复的余量保留。
- `$2018/$2019/$201A/$201E bit0` 保持软件计数、周期、开关及待投递事件。
  根据连续256 Hz壁钟批量推进，保留小数余量，事件仍合并为一个pending位；
  `SysGetKey`不消费Timer事件，关闭游戏Timer也不停止宿主画面刷新。
- E.BIN bank 9 `$8A7C→$8195` 为消息框。原版宽度固定，**不是按文字长度收窄**：
  主边框x=11..146，按每行16字节换行（GBK不拆对），最多5行，行高16。
  高度取决于行数，另含右、下阴影；保留ROM整行边界附加空行的行为。
- “百草地”实参为`timeout=100`。一行边框y=37..57，含阴影的保存/恢复区为
  `(11,37)..(148,59)`，高度23，文字起点`(15,39)`。
  超时期间临时采用周期1，按原Timer源计算独立截止时间（约0.9秒，另受宿主唤醒延迟影响），
  到时或有按键才返回；timeout=0等待按键。返回时恢复背景及原Timer配置。

新增测试在PC执行真实ROM的布局、参数构造、等待循环及Timer保存/恢复控制流；
只替换外部绘图、输入和分配接口。Timer开关与25组计数/回绕组合另直接对照真实
`$7B8B`指令。原生辅助函数测试覆盖GBK边界、空串、最大行数、背景逐字节恢复、
超时、提前按键、关闭后的屏幕刷新，以及多次短计时与一次长计时的一致性。

### QUERY-BOX-1：公共确认框修复（2026-09-05）
